실패 알림은 돌다가 실패한 일을 알려 줍니다. 일정이 시작되지 않은 날에는 실패할 일이 없으므로 알림도 울리지 않습니다. 그래서 오류를 알리는 장치와 별도로, 정해진 시각에 성공 신호가 도착했는지를 지켜보는 장치가 하나 더 필요합니다. 리도의 글 자동화 기록에도 오전 게시가 빠진 날이 두 번 있었고, 기록에는 두 번 모두 오류의 원인이 적혀 있지만 누가 어떻게 알았는지는 적혀 있지 않습니다.

2026년 11월 14일 확인한 공식 문서(n8n, GitHub Actions, Healthchecks.io)와 리도의 작업 기록, 공개 저장소의 커밋 기록 기준입니다. 고객사 프로젝트가 아니라 리도 자신의 게시 자동화 사례이며, 아래 점검 카드가 사고를 줄인다는 측정은 이 글에 없습니다.

## 실패 알림을 달아 두면 안 돌아간 날도 알 수 있습니까?

그렇게 믿을 근거는 문서에서 찾지 못했습니다. 세 도구의 문서가 설명하는 범위를 보면 이유가 보입니다.

[n8n의 Error Trigger 문서](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger/)가 다루는 것은 연결된 워크플로가 실패했을 때입니다. 실패한 워크플로와 오류 내용을 받아 별도의 오류 워크플로를 돌리는 방식이고, 일정 시각에 아무 실행도 만들어지지 않은 경우는 문서에 나오지 않습니다. 시작 단계인 트리거 노드에서 난 오류는 실행 정보가 없는 별도 형식으로 전달된다고 적혀 있어, 시작 단계의 일부 오류는 다룹니다. 같은 문서에는 수동으로 실행해서는 오류 워크플로를 시험할 수 없고 자동 실행이 오류를 낼 때만 작동한다는 내용도 있습니다. 알림이 제대로 달려 있는지는 자동 실행을 실제로 실패시켜 봐야 확인할 수 있다는 뜻입니다.

[GitHub Actions 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)의 예약 실행(schedule) 항목에는 알림 대상에 관한 문장이 있습니다. 예약 실행의 알림은 워크플로 파일에서 cron 문구를 마지막으로 고친 사용자에게 갑니다. 또 비활성화된 예약 워크플로는 쓰기 권한이 있는 사람이 cron 일정을 바꾸는 커밋을 올리면 다시 활성화되고, 그 사람이 이후 실행의 행위자가 됩니다. 알림은 마지막으로 일정 문구를 고친 사람에게 가며 담당자 지정과는 관계가 없습니다. 그 사람이 자동화를 맡은 사람과 같은지는 문서가 보장하지 않습니다.

[Healthchecks.io](https://healthchecks.io/docs/)는 반대 방향에서 접근합니다. 작업이 끝날 때마다 신호(ping)를 보내게 해 두고, 신호가 제때 오면 조용히 있다가 오지 않으면 알립니다. [cron 감시 안내](https://healthchecks.io/docs/monitoring_cron_jobs/)는 이 방식으로 잡을 수 있는 실패로 컴퓨터 전체가 꺼진 경우, cron(정해진 시각에 작업을 실행하는 유닉스 도구)이 돌지 않거나 설정이 잘못된 경우, 작업이 0이 아닌 종료 코드로 끝난 경우, 작업이 비정상적으로 오래 도는 경우를 듭니다. 기존 cron의 MAILTO(작업 결과를 메일로 받는 설정)에 대해서는 컴퓨터가 꺼지거나 네트워크가 끊기면 알림을 받지 못하고, 작업이 출력을 낼 때마다 메일이 와서 오류가 그 사이에 묻힐 수 있다고 한계를 적었습니다.

## 리도의 글 자동화에서는 빠진 날을 어떻게 알았습니까?

DMS.Labs에는 매일 오전 9시에 시작해 Work, Writing, Ideas를 돌아가며 한영 글 한 편을 올리는 자동화가 있고, 이 글도 그 자동화가 만들었습니다. 이 자동화의 기억 기록에는 빠진 날이 두 번 적혀 있습니다. 10월 29일 회차는 모델 호출이 요청 한도 오류(429)로 끝나 글이 올라가지 않았고, 소급해서 올리지 않았습니다. 11월 2일 회차는 모델 키 오류로 중간에 끊겼고, 그 차례였던 Writing 글을 11월 3일에 올려 복구했습니다.

공개 저장소의 커밋 기록은 같은 사실을 따로 보여 줍니다. 10월 27일부터 11월 3일까지 8일 가운데 오전 9시대에 한영 글 게시 커밋이 있는 날은 6일이고, 10월 29일과 11월 2일에는 없습니다. 다만 그 두 날에도 다른 작업이 올린 광통신 교안 커밋은 저녁에 들어와 있습니다. 저장소에 커밋이 있다는 사실만으로는 이 자동화가 돌았는지 알 수 없습니다. 이 자동화의 몫인 오전 커밋을 따로 봐야 합니다.

기록이 적지 않은 것도 있습니다. 두 날을 누가 어떤 경로로 알아챘는지, 그 사이 알림이 어디로 갔는지는 남아 있지 않습니다. 확인된 것은 글이 빠졌다는 사실과 기록된 원인뿐이라서, 이 글은 알림이 울렸다고도 울리지 않았다고도 말하지 않습니다. 리도가 이 자동화를 운영하며 지키는 기준 하나는 있습니다. 예약 설정이 활성 상태로 보인다는 것은 그날 결과가 있다는 뜻이 아니라는 점입니다. 그래서 그날의 결과를 공개 저장소와 공개 화면에서 직접 확인합니다.

## 무엇을 지켜보면 됩니까?

바깥에 남는 성공 신호를 하나 정하고, 그 신호가 정해진 시각 안에 생겼는지를 봅니다. 아래 표는 위 문서들의 설명과 이 글의 시험을 바탕으로 오류 알림과 성공 신호 점검이 각각 잡는 것을 나눈 것입니다.

| 실패의 모습 | 오류 알림 | 성공 신호 점검 |
|---|---|---|
| 돌다가 오류로 끝났다 | 잡음 | 신호가 없어 잡음 |
| 일정이 시작되지 않았다 | 이 경우는 문서에 나오지 않음 | 신호가 없어 잡음 |
| 컴퓨터가 꺼지거나 네트워크가 끊겼다 | 알림을 보낼 쪽도 같이 멈추면 못 잡음 | 점검이 다른 곳에서 돌면 잡음 |
| 끝까지 돌았지만 결과가 틀렸다 | 못 잡음 | 못 잡음 |

표의 마지막 줄은 두 장치 모두 해 주지 못하는 일입니다. 결과를 바깥에서 다시 읽는 방법은 [성공 출력 뒤에 다시 읽기](/works/read-back-after-success)에서 다뤘습니다.

내 업무에 옮기려면 아래 다섯 칸을 한 장에 적어 두는 것이 출발점이 됩니다. 이 카드는 DMS.Labs의 제안이며 고객 프로젝트에서 검증한 양식이 아닙니다.

| 칸 | 적을 것 |
|---|---|
| 돌아야 하는 때 | 주기와 허용 지연(예: 매일 오전 9시, 늦어도 10시까지) |
| 성공 신호 | 일이 끝난 뒤 바깥에 남는 한 줄(표의 새 행, 파일, 공개 화면) |
| 신호가 없을 때 받는 사람 | 이름 한 명과 서로 다른 알림 길 두 개 |
| 알림 길 시험일 | 일부러 신호를 빼 보고 알림이 도착한 마지막 날짜 |
| 멈출 때 끄는 법 | 일부러 멈추는 동안 점검을 일시정지하고 다시 켤 날짜 |

직원 5명인 인테리어 견적 업체가 매일 아침 견적 요청 메일을 표로 옮기는 자동화를 쓴다고 가정해 보겠습니다. 가정이므로 실제 고객 사례가 아닙니다. 이 업체의 성공 신호는 표 맨 아래에 그날 날짜가 적힌 행이 생기는 것이고, 오전 10시까지 그 행이 없으면 담당자에게 문자와 메일이 따로 가도록 합니다. 오류 알림이 이미 있어도 이 점검은 따로 둡니다. 자동화가 아예 시작되지 않은 날은 오류 알림에 걸리지 않기 때문입니다. 담당자를 정하는 방법은 [자동화를 만든 사람이 없는 날](/works/automation-owner-card)에서 다뤘습니다.

## 알림 길은 시험해 봤습니까?

일부러 신호를 빼서 시험해 봐야 합니다. 앞서 본 n8n 문서처럼 도구에 따라 수동 실행으로는 오류 알림을 시험할 수 없는 경우가 있고, 알림이 나가는 길은 쓰이기 전에는 확인되지 않기 때문입니다.

이 글을 쓰며 PowerShell로 임시 폴더에 네 가지 경우를 만들어 보았습니다. 작업이 성공하면 성공 신호 파일을 쓰고 오류가 나면 알림 파일을 쓰는 오류 처리를 붙였습니다. A는 성공한 작업, B는 오류로 끝난 작업, C는 일정이 작업을 아예 부르지 않은 경우, D는 세 시간 전에 남은 성공 신호 파일만 있는 경우입니다. 허용 지연은 90분으로 했습니다.

| 경우 | 오류 처리가 쓴 알림 | 성공 신호 점검 결과 |
|---|---|---|
| A 성공 | 없음 | OK |
| B 오류로 끝남 | 1건 | NEVER |
| C 호출되지 않음 | 없음 | NEVER |
| D 3시간 전 신호만 있음 | 없음 | LATE(180분) |

오류 처리가 반응한 것은 B 하나였습니다. 성공 신호 점검은 A를 뺀 세 경우를 모두 잡았습니다. NEVER는 성공 신호 파일이 아직 없다는 뜻이어서, 이 점검만으로는 B와 C를 가를 수 없습니다. 원인을 가르는 일은 오류 알림이 맡고, 일정이 시작되지 않은 날을 잡는 일은 성공 신호 점검이 맡는 식으로 둘이 서로를 채웁니다.

점검에 쓴 함수는 이렇습니다.

```powershell
function Test-Heartbeat($path, $maxAgeMin) {
  if (-not (Test-Path $path)) { return 'NEVER' }
  $age = ((Get-Date) - (Get-Item $path).LastWriteTime).TotalMinutes
  if ($age -gt $maxAgeMin) { return "LATE($([int]$age)min)" }
  return 'OK'
}
```

이 시험은 임시 폴더 안의 파일 규칙을 따져 본 것입니다. 작업 스케줄러나 n8n, GitHub Actions 같은 실제 예약 도구에서 돌려 본 것은 아닙니다. 점검이 작업과 같은 컴퓨터에서 돌 때 컴퓨터가 꺼지면 둘이 함께 멈춘다는 점도 시험하지 않았고, 그 부분은 Healthchecks.io 문서의 설명에 기댄 것입니다.

## 알림을 많이 달아 두면 안전합니까?

그렇지 않습니다. 알림이 도착하는 길의 수와 알림이 울리는 횟수는 다른 문제입니다. Healthchecks.io 문서는 한 채널이 막힐 때를 대비해 알림 길을 여러 개 두라고 권합니다. 같은 문서는 작업이 출력을 낼 때마다 메일이 오는 기존 방식에서 오류가 그 사이에 묻힐 수 있다고도 적었습니다. 길은 둘 이상으로 하고, 울리는 때는 신호가 오지 않았을 때로 한정하는 편이 맞습니다. 점검 중인 작업이 하나라도 멈춰 있으면 매시간이나 매일 알림 메일을 되풀이해 보내는 설정도 문서에 있습니다. 한 번 놓친 알림이 그대로 묻히지 않게 하려는 장치입니다.

## 이 기록이 말하지 못하는 것은 무엇입니까?

빠진 두 날은 한 자동화의 8일치 기록에서 나온 것이어서 전체 빈도를 말해 주지 않습니다. 그 두 날 알림이 있었는지는 확인하지 못했습니다. 성공 신호 점검이 사고를 줄였다는 측정도 없습니다. 이 글은 문서가 설명한 방식과 임시 폴더 시험을 합쳐 점검 카드를 제안한 것이고, 고객 현장에서 검증한 절차가 아닙니다.

도구 문서의 내용은 2026년 11월 14일 시점입니다. 문서가 바뀌면 같은 설명이 유지되지 않을 수 있습니다. GitHub Actions의 알림 대상 설명도 이 날짜의 문서 기준입니다.

## 다음에 볼 것

자동화마다 무엇을 성공 신호로 삼고 누가 받을지를 업무 단위로 설계하려면 [DMS.Labs 업무 자동화](/automation) 페이지를 보실 수 있습니다. 상담이 필요하면 [문의 페이지](/contact)로 연락하시면 됩니다. 이 글의 범위는 리도 자신의 글 자동화 기록과 공식 문서이며, 도입 비용이나 절감 시간, 문의와 매출 효과를 약속하지 않습니다. 자동화가 한 일을 한 줄로 남기는 방법은 [자동화가 한 일, 한 줄로 남기기](/works/automation-run-record)에서 다뤘습니다.

본문의 두 이미지는 설명용으로 새로 생성한 장면입니다. 실제 작업 화면이나 고객 현장을 촬영한 사진이 아닙니다.
