A contact form fails more quietly than almost anything else on a website. The visitor presses the button, sees a thank-you message, and the email never shows up. The send button may sit under the keyboard on a phone. While the pages load and the articles read well, nobody notices, and the person who wanted to reach you simply waits. This is a practical guide, not a client case study or a claim about results. It describes a check a small team can run before publishing a form and again after changing it.

The standard is one question: can a person on your side actually receive and read the enquiry? That means checking both ends, the visitor's side and the inbox.

## The visitor's side: can they understand the fields and finish?

Start by using the form the way a visitor would. Every field needs a visible label. If the only hint is faint placeholder text, it disappears as soon as someone types, and they can no longer see what the field was for. [The W3C's guidance on form labels](https://www.w3.org/WAI/tutorials/forms/labels/) says a label should be associated with its input so assistive technology can announce it. A quick test: click the label text. If the cursor jumps into the field, the association exists.

Browsers can fill in names and email addresses when the `autocomplete` attribute is set correctly. [MDN documents the available values](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/autocomplete). Give the email field the email input type so phones open a suitable keyboard. Say in words which fields are required rather than relying on an asterisk alone, since not everyone knows what the asterisk means.

Then fill the form in wrongly on purpose. Leave the email field empty, or type an address without an at sign. The error message should say which field is wrong and why. [WCAG 2.2's explanation of error identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html) says that when an error is detected automatically, the item in error is identified and the error is described to the user in text. A red border alone tells nothing to someone who cannot distinguish the colour. Check, too, that a long message survives a failed submission. Few people will retype three paragraphs.

Look at the moment right after sending. If the button stays active until the response arrives, the same enquiry can be submitted two or three times. If it is disabled but nothing explains why, visitors assume the page froze and reload it. A short "sending" message helps, and the result, success or failure, has to appear as text. [WCAG 2.2's explanation of status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) says such messages should be programmatically determinable so assistive technology can announce them without moving focus. How you build that varies by site. A success signal that only sighted users can perceive is an incomplete one.

Repeat the run on a narrow screen. With the keyboard open, is the send button still reachable? Does a long message push the field off screen? Is the consent text cut off? Then put the mouse aside and press Tab from the first field to the button, checking that the order matches what the eye sees.

## The server's side: accepted is not delivered

Passing the visitor's side is only half the job. Next, follow the message. A form usually passes through server code or an outside service that turns it into an email or a database record. That path contains three separate events. The server received the request. The mail service accepted the sending job. The message reached the recipient's inbox. The success text on the screen normally appears after the first or second event. Nobody can know the third unless the person who deployed the form looks.

So begin by sending a real enquiry. Mark it clearly as a test, then look for it in the inbox your team actually uses. Confirm that the subject and body contain everything that was typed, and that the visitor's address is set as the reply-to. Avoid putting the visitor's address in the From field. Your server would then appear to be sending mail as someone else's address, and a receiving server may treat it as forgery. The common pattern is a From address on your own domain and the visitor's address in Reply-To.

If the site publishes in two languages, submit each language's form separately. An English form that quietly reuses the Korean handler may return Korean error text or a Korean auto-reply. Recording which language page an enquiry came from, in the subject or body, makes it easier for whoever replies to choose a language.

## Sender authentication: spam-folder delivery is not delivery

If the test message does not appear, check the spam folder first. A message found there was accepted but only half delivered. The first suspect is sender authentication.

[Google's email sender guidelines](https://support.google.com/a/answer/81126) say that since 1 February 2024 every sender to personal Gmail accounts must set up SPF or DKIM for the sending domain. Senders of more than 5,000 messages a day to Gmail must also set up DMARC. The same page warns that unauthenticated messages might be marked as spam or rejected with a 5.7.26 error. A small contact form will almost never reach 5,000 messages a day, so the bulk-sender rules need not apply to it. Still, the same guidance recommends setting up SPF, DKIM and DMARC for your domains, and that is a sensible line to put on the checklist.

The three do different jobs. SPF lists in DNS the servers allowed to send mail for your domain. DKIM adds a signature so the receiving server can verify the domain owner sent the message. DMARC tells receiving servers what to do with mail that fails SPF or DKIM, and it is defined in [RFC 7489](https://www.rfc-editor.org/rfc/rfc7489). If the form uses an outside mail-sending service, follow that service's instructions to confirm it is included in your SPF record and that DKIM signing is on. The day you add a new service is the day this check is due again.

The most direct way to verify is to open the original headers of the test message. In Gmail, the message menu has a "show original" option that lists SPF, DKIM and DMARC results as pass or fail. If anything failed, correct the DNS record and send another test. DNS changes can take time to spread, so after one failure, wait and repeat the same test before layering on new settings.

## When sending fails, who finds out?

The question most often left off the checklist is who learns that a send failed. If the mail service returns a temporary error, the screen should show a failure message and either keep the enquiry or point to another way of getting in touch. If the error appears only in a server log that nobody reads, enquiries keep vanishing.

A small team does not need an elaborate setup. Start by storing each enquiry in one place separately from the email, and mark the case where it was stored but the email failed. Put a visible alternative on the page as well, such as a contact email address or phone number. When the form breaks, that is the route that keeps a visitor from giving up.

If you have more than one deployment environment, check one more thing. Make sure the recipient address or sending key used during testing is not the one live in production, and that production keys are not open in the test environment. Keep secrets out of the repository and in the hosting service's environment variables. After changing a value, send a test through the new deployment, because a changed variable without a redeploy can leave the old value running.

Defence against spam submissions is part of the form too. Hidden fields, short time limits and rate limits can reduce automated entries. Check on the same list that these measures do not block real visitors. Can the human check be solved with a screen reader and a keyboard? Does it open on a phone? If enquiries drop to zero the day you strengthen protection, suspect first that real messages are being blocked along with the spam.

## Leave a record

Write down what you confirmed so the next change starts from it. It does not need to be long. Note the date, the address and language of the page tested, whether the test message reached the inbox or the spam folder, the SPF, DKIM and DMARC results, whether a phone user could finish, and any open problems, one line each. Repeat the same test whenever you change the domain's mail settings, switch sending services, or add a field.

This record is not a showcase. It tells the next person where to look first. Confidence in a contact form comes from a test message you saw in the inbox and from the authentication results, not from one success screen. Once that is confirmed, the form can stay live.
