AI의 답이 정해 둔 JSON 칸에 정확히 들어맞는다는 것과 그 칸의 값이 맞다는 것은 서로 다른 이야기입니다. OpenAI와 Anthropic의 구조화된 출력 문서는 앞의 것을 약속하고, 값이 업무에 맞는지는 애플리케이션이 따로 검사해야 한다고 적습니다. 이 글에서 손으로 만든 견적 메일 모의 답 9건을 검사해 보니, 형식 검사를 통과한 8건 가운데 업무 규칙까지 통과한 것은 4건이었고 실제로 맞는 것은 3건이었습니다.

2026년 11월 27일 확인한 공식 문서 기준입니다. 근거는 [OpenAI의 구조화된 출력 안내](https://developers.openai.com/api/docs/guides/structured-outputs)와 [Anthropic의 구조화된 출력 안내](https://docs.anthropic.com/en/docs/build-with-claude/structured-outputs), 그리고 직접 만든 모의 시험입니다. 고객 사례가 아니며, 실제 모델에 요청을 보내 시험한 것도 아닙니다.

## 구조화된 출력은 무엇을 보장합니까?

정해 둔 JSON 형식에 맞는 답이 나오게 하는 것을 보장하고, 그 안의 값이 맞는지는 보장하지 않습니다.

OpenAI 문서는 구조화된 출력이 거절이 아닌 완료된 답을 사용자가 준 JSON 스키마에 맞춘다고 설명합니다. 필수 칸과 enum(정해 둔 선택지) 값이 스키마를 따른다는 뜻입니다. 이전 방식인 JSON 모드와의 차이도 적혀 있습니다. 둘 다 올바른 JSON을 내지만 스키마까지 지키는 것은 구조화된 출력뿐이고, OpenAI는 가능하면 구조화된 출력을 쓰라고 권합니다.

Anthropic 문서도 같은 방향입니다. 제약 있는 디코딩(출력 단계에서 스키마를 벗어난 글자를 고르지 못하게 하는 방식)으로 JSON 문법 오류가 없고, 필드 타입과 필수 칸이 지켜지며, 스키마 위반 때문에 다시 요청할 필요가 없다고 적습니다.

메일에서 이름과 금액을 뽑아 표에 넣는 자동화에서 이것은 큰 도움입니다. 줄바꿈이 잘못 들어가거나 숫자 칸에 글자가 들어가 표가 깨지는 일이 줄어듭니다. 다만 두 문서가 약속하는 범위는 형식에서 멈춥니다.

## 문서가 보장하지 않는 것은 무엇입니까?

두 문서 모두 형식이 어긋나는 경우와, 형식은 맞아도 값이 틀릴 수 있는 경우를 직접 적어 둡니다.

| 상황 | 문서에 적힌 내용 |
|---|---|
| 거절 | OpenAI는 `refusal` 칸으로 거절을 알립니다. Anthropic은 `stop_reason`이 `refusal`이고 상태 코드는 200이며 토큰 비용이 청구된다고 적고, 이때 출력이 스키마와 맞지 않을 수 있다고 합니다. |
| 잘림 | Anthropic은 `max_tokens`에 걸리면 출력이 불완전하고 스키마와 맞지 않을 수 있다고 합니다. OpenAI는 응답 상태가 incomplete이고 이유가 `max_output_tokens` 또는 `content_filter`일 수 있다고 합니다. |
| 스키마와 무관한 입력 | OpenAI는 모델이 항상 스키마에 맞추려 하므로, 입력이 스키마와 전혀 무관하면 환각이 생길 수 있다고 적습니다. 그런 입력에는 빈 값이나 정해 둔 문장을 돌려주라고 프롬프트에 쓰라고 권합니다. |
| 값의 실수 | OpenAI는 구조화된 출력에도 실수가 있을 수 있다고 하며, 지시문을 고치거나 예시를 넣거나 작업을 잘게 나누라고 안내합니다. |
| 스키마가 말하지 못하는 업무 규칙 | OpenAI는 스키마가 표현하지 않는 업무 규칙을 애플리케이션이 검증해야 한다고 적습니다. |
| enum 대소문자 | Anthropic은 enum 값의 대소문자를 보장하지 않으며, 비교할 때 대소문자를 무시하라고 합니다. |
| 숫자 범위 같은 제약 | Anthropic의 SDK는 `minimum`, `maxLength` 같은 지원되지 않는 제약을 스키마에서 빼고 설명문에 옮깁니다. 응답을 검증하는 도우미를 쓰면 그 제약을 코드에서 다시 확인한다고 합니다. |

필수 칸에 대한 문장도 하나 짚어 둡니다. OpenAI 문서에서 모든 칸은 필수이고 모델은 칸마다 값을 돌려줍니다. 비어도 되는 칸은 `null`을 허용하는 합집합 형식으로 흉내 냅니다. 이 문장과 위의 환각 안내를 이어 보면, 메일에 없는 정보도 빈칸 대신 그럴듯한 값으로 채워질 수 있습니다. 문서가 직접 이렇게 말한 것은 아니고, 두 문장을 잇는 제 해석입니다.

## 형식은 맞고 값은 틀린 답이 얼마나 나옵니까?

실제 모델로 잰 비율은 모릅니다. 손으로 만든 모의 답 9건에서는 형식을 통과한 8건 가운데 5건이 틀렸습니다.

가상의 부품 업체가 견적 요청 메일 9통에서 업체명, 품목, 수량, 단가, 합계, 납기, 긴급 여부 일곱 칸을 뽑는다고 가정했습니다. 요청일은 2026년 11월 2일입니다. 형식 검사는 칸이 모두 있고 타입이 맞는지 봅니다. 업무 규칙 검사는 합계가 수량 곱하기 단가인지, 납기가 요청일 이후인지, 업체명이 메일 본문에 있는지, 광고 메일은 아닌지 봅니다.

| 번호 | AI 답의 상태 | 형식 검사 | 업무 규칙 검사 | 원문과 비교 |
|---|---|---|---|---|
| 1 | 정상 | 통과 | 통과 | 맞음 |
| 2 | 40개, 개당 1,200원인데 합계가 46,000원(맞는 값은 48,000원) | 통과 | 합계가 맞지 않음 | 틀림 |
| 3 | 납기 연도가 2025년 | 통과 | 납기가 요청일 이전 | 틀림 |
| 4 | 업체명에 다른 메일의 업체명이 들어감 | 통과 | 업체명이 본문에 없음 | 틀림 |
| 5 | 광고 메일인데 일곱 칸을 모두 채움 | 통과 | 광고 문구 감지 | 틀림 |
| 6 | 답이 날짜 중간에서 끊김 | 파싱 실패 | 해당 없음 | 해당 없음 |
| 7 | 정상 | 통과 | 통과 | 맞음 |
| 8 | 정상 | 통과 | 통과 | 맞음 |
| 9 | 단가를 1,020원으로 읽고 합계 102,000원을 그에 맞춰 계산(메일에는 1,200원) | 통과 | 통과 | 틀림 |

9건 가운데 8건이 읽혔고, 8건이 형식 검사를 통과했고, 4건이 업무 규칙까지 통과했고, 원문과 같은 것은 3건입니다. 9번이 눈에 띕니다. 단가를 잘못 읽었지만 합계가 그 단가에 맞게 계산되어 있어 칸끼리의 모순이 없습니다. 이런 틀림은 값끼리 맞춰 보는 규칙으로는 잡히지 않고, 원문과 나란히 놓아야 보입니다.

이 9건의 AI 답은 제가 손으로 만들었고, 틀린 방식도 제가 골랐습니다. 검사 코드도 제가 쓴 규칙을 옮긴 것이라 결과는 처음부터 정해져 있었습니다. 이 시험이 보여 주는 것은 틀림의 비율이 아니라, 어떤 검사가 어떤 종류의 틀림을 잡는지입니다.

## 형식 검사 뒤에 어떤 규칙을 두면 됩니까?

응답 상태, 칸끼리의 일치, 원문과의 일치, 해당 없는 입력의 처리 네 가지로 나누어 두면, 모의 시험의 틀림이 어느 단계에서 잡히고 어느 것이 빠져나가는지 보입니다.

| 규칙 | 무엇을 보는가 | 모의 시험의 예 | 한계 |
|---|---|---|---|
| 응답 상태 먼저 | 완료인지 거절인지 잘림인지를 읽고 나서 파싱 | 6번 | 잘린 답을 한도만 올려 다시 받을 때는 같은 메일을 두 번 처리하지 않게 해야 합니다 |
| 칸끼리 맞춤 | 합계가 수량 곱하기 단가인지, 날짜가 범위 안인지 | 2번, 3번 | 틀린 값에 맞춰 다른 칸도 계산되어 있으면 통과합니다(9번) |
| 원문과 맞춤 | 업체명이 본문에 실제로 있는지, 단가 숫자가 본문에 있는지 | 4번 | 표기가 다르면(예: 한글로 쓴 숫자) 틀리지 않았는데 걸릴 수 있습니다 |
| 해당 없음 처리 | 대상이 아닌 입력에는 빈 값이나 정해 둔 문장을 돌려주게 하고, 코드에서도 다시 확인 | 5번 | 무엇이 해당 없음인지는 사람이 미리 정해 두어야 합니다 |

원문과 맞추는 규칙에 단가 숫자를 넣으면 9번의 1,020원도 걸러질 것으로 보입니다. 이 시험에서는 그 규칙을 넣지 않았고, 실제 메일의 다양한 표기에서 얼마나 잘 작동하는지도 확인하지 않았습니다.

6번처럼 답이 잘렸을 때 다시 받는 방법과, 다시 받다가 같은 일을 두 번 하지 않게 하는 방법은 [AI 자동화 재시작 기준](/works/ai-automation-safe-retry)에서 다뤘습니다.

## 규칙이 통과시킨 틀림은 누가 봅니까?

규칙을 통과한 결과 중 일부를 사람이 원문과 나란히 놓고 보는 방식이 필요합니다. 이것은 DMS.Labs의 제안이고, 시험해서 얻은 기준이 아닙니다.

규칙은 사람이 미리 떠올린 틀림만 잡습니다. 9번처럼 아무도 규칙으로 쓰지 않은 틀림은 지나갑니다. 그래서 처음에는 전부, 규칙이 계속 통과하는 시기에는 일부를 뽑아 원문과 대조하는 쪽이 안전합니다. 얼마나 뽑을지는 틀렸을 때의 비용에 따라 달라지므로 이 글에서 숫자를 정하지 않습니다.

누가 보는지는 미리 정해야 합니다. 검수자를 정하는 8칸 카드는 [AI 결과 검수자 정하기](/works/ai-output-reviewer-card)에, 성공으로 표시된 결과를 바깥에서 다시 읽는 방법은 [성공 출력 뒤에 다시 읽기](/works/read-back-after-success)에 있습니다. 어떤 결과를 합격으로 볼지의 기준은 [AI 스킬 합격 기준](/works/ai-skill-acceptance-tests)이 다룹니다.

## 다섯 칸 점검 카드는 어떻게 씁니까?

AI의 답을 칸에 받는 자동화마다 아래 다섯 칸을 한 장에 적어 두는 것을 제안합니다. 오른쪽 열은 앞의 모의 시험을 쓴 가정 예시입니다. 직원 여덟 명 규모의 가상 부품 업체가 견적 요청 메일에서 일곱 칸을 뽑아 견적서 초안에 넣는 경우이며, 실제 고객 사례가 아닙니다.

| 칸 | 적을 것 | 가정 예시 |
|---|---|---|
| 응답 상태 | 정상 완료가 아닌 응답(거절, 잘림, 오류)을 어디로 보낼지 | 잘린 답은 처리하지 않고 보류 목록에 두며, 한도를 올려 한 번만 다시 받습니다 |
| 형식 검사 | 스키마가 맞추는 것과 코드로 다시 확인할 것 | 필수 칸과 타입은 스키마로 두고, 숫자 범위와 enum 대소문자는 코드에서 확인합니다 |
| 값 규칙 | 칸끼리, 그리고 원문과 맞는지 | 합계, 납기, 업체명과 단가 숫자가 본문에 있는지 봅니다 |
| 못 채우는 값 | 정보가 없을 때 칸에 넣을 값 | 메일에 없는 칸은 `null`로 두고, 광고 메일은 모든 칸을 비웁니다 |
| 사람에게 넘기는 조건 | 규칙이 하나라도 실패하면 누가 보는지, 통과한 것은 얼마나 뽑아 볼지 | 실패한 건은 담당자가 원문과 보고, 통과한 건도 일부를 대조합니다 |

이 카드를 적어 두면 자동화를 만든 사람이 자리를 비워도 다른 사람이 같은 기준으로 검사를 이어 갈 수 있습니다. 담당자를 정하는 방법은 [자동화를 만든 사람이 없는 날](/works/automation-owner-card)에서, 자동화가 한 일을 한 줄로 남기는 방법은 [자동화가 한 일, 한 줄로 남기기](/works/automation-run-record)에서 다뤘습니다.

## 이 글이 말하지 못하는 것은 무엇입니까?

실제 모델에 요청을 보내 시험하지 않았습니다. 구조화된 출력이 실제 업무 메일에서 얼마나 자주 틀리는지는 모릅니다. 9건의 모의 답은 제가 만들었고, 틀림의 종류와 비율은 그 선택의 결과입니다.

두 문서는 웹 페이지라서 바뀔 수 있습니다. 위 내용은 2026년 11월 27일에 읽은 판본이며, 지원하는 스키마 키워드와 모델 범위는 문서마다 따로 적혀 있어 여기서 다 옮기지 않았습니다. Google 같은 다른 회사나 직접 설치하는 모델의 구조화된 출력은 읽지 않았습니다. 사람이 표본을 얼마나 볼지, 어떤 규칙이 현장에서 오탐을 내는지는 이 글에서 시험하지 않았습니다.
