시험 실행(dry run)은 자동화가 바깥에 손대지 않고 무엇을 하려는지 미리 보여 주는 기능입니다. 다만 보여 주는 범위가 도구마다 다릅니다. 권한만 확인하는 도구가 있고, 저장 직전까지 모든 단계를 거치는 도구가 있고, 바꿀 내용을 목록으로 보고하는 도구가 있습니다. 앞 단계 결과에 따라 달라지는 일이나 시험 실행을 지원하지 않는 단계는 보고서에 나오지 않을 수 있어서, 시험 실행이 깨끗하다는 이유만으로 자동화를 켜도 된다고 판단하면 안 됩니다.

2026년 11월 21일 확인한 공식 자료(Ansible 문서, 쿠버네티스 문서, AWS CLI 문서)와 내 컴퓨터에서 돌린 모의 자동화 시험 기준입니다. 고객사 프로젝트 사례가 아니며, 아래 카드가 사고를 줄인다는 측정은 이 글에 없습니다.

## 시험 실행이 깨끗하면 바로 켜도 됩니까?

그렇지 않습니다. 시험 실행은 실제 실행을 흉내 내는 일이어서 흉내가 닿지 않는 부분이 남습니다.

[Ansible 문서](https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_checkmode.html)는 검사 모드(check mode)를 이렇게 설명합니다. 원격 시스템에 아무 변경도 하지 않고 실행하며, 검사 모드를 지원하는 모듈은 바꿨을 내용을 보고합니다. 지원하지 않는 모듈은 아무것도 보고하지 않고 아무것도 하지 않습니다. 같은 문서는 검사 모드가 시뮬레이션일 뿐이라고 적고, 앞 단계의 결과(등록한 변수)에 따라 갈리는 조건 단계는 출력이 나오지 않는다고 덧붙입니다.

그래서 시험 실행 보고서는 도구가 알려 줄 수 있는 범위만 담긴 예고로 읽어야 합니다. 보고서에 없는 일이 실제 실행에서도 일어나지 않는다는 보증은 아닙니다.

## 도구마다 시험 실행이 보여 주는 범위가 같습니까?

다릅니다. 이번에 읽은 문서 세 곳만 봐도 세 가지로 갈렸습니다.

| 도구 | 시험 실행이 하는 일 | 문서가 밝힌 한계 |
|---|---|---|
| AWS CLI (EC2 인스턴스 시작 명령의 `--dry-run`) | 요청을 실제로 보내지 않고 필요한 권한이 있는지 확인합니다. 권한이 있으면 `DryRunOperation`, 없으면 `UnauthorizedOperation` 오류 응답이 돌아옵니다 | 문서가 설명하는 확인 대상은 권한입니다 |
| 쿠버네티스 (`dryRun=All`) | 요청이 거치는 단계(승인 단계, 검증, 병합 충돌 확인)를 저장 직전까지 모두 거칩니다. 저장과 다른 부작용은 없다고 보장합니다 | 이름, 고유번호, 시각처럼 저장 전에 만들어지는 값은 실제 실행 때와 달라질 수 있어 믿지 말라고 합니다 |
| Ansible (`--check`) | 지원하는 모듈이 바꿨을 내용을 보고합니다 | 지원하지 않는 모듈은 아무 보고도 없고, 앞 결과에 따른 조건 단계는 출력이 나오지 않습니다 |

[쿠버네티스 API 문서](https://kubernetes.io/docs/reference/using-api/api-concepts/)의 시험 실행 절은 응답이 실제 실행 응답과 최대한 가깝다고 설명합니다. 그러면서도 생성되는 값은 다를 수 있다고 따로 경고합니다. [AWS CLI 문서](https://docs.aws.amazon.com/cli/latest/reference/ec2/run-instances.html)에서는 눈여겨볼 점이 하나 더 있습니다. 권한이 있다는 대답이 오류 응답의 모양으로 옵니다. 오류 응답을 모두 실패로 세는 자동화는 이 대답을 실패로 읽을 수 있습니다. 이 부분은 문서 문장에서 이끌어 낸 제 해석이고, 실제 도구로 시험하지는 않았습니다.

## 시험 실행 보고서에서 빠지는 단계도 있습니까?

있습니다. Ansible 문서가 적은 두 경우를 코드로 옮겨, 보고서가 진짜 실행과 어떻게 달라지는지 내 컴퓨터에서 확인했습니다. 다섯 단계짜리 모의 자동화를 Node로 만들었습니다. 실제 서비스가 아니라 대기 명단 안내 메일을 보내는 가상의 흐름입니다.

1. 대기 명단 읽기
2. 안내 문구 만들기
3. 메일 보내기(시험 실행을 지원하고, 보낼 통수만 보고합니다)
4. 발송 기록 한 줄 추가(3단계가 돌려주는 번호가 있어야 실행되는 조건 단계입니다)
5. 외부 시트 갱신(시험 실행을 지원하지 않습니다)

시험 실행과 진짜 실행을 한 번씩 돌린 결과입니다.

| 단계 | 시험 실행 보고 | 진짜 실행 |
|---|---|---|
| 1 명단 읽기 | 3명 읽음 | 3명 읽음 |
| 2 문구 만들기 | 문구 1개 | 문구 1개 |
| 3 메일 보내기 | 3통을 보낼 예정 | 3통 보냄, 번호 msg-1007 |
| 4 발송 기록 | 보고 없음 | 기록 msg-1007 |
| 5 시트 갱신 | 보고 없음 | 실패: 403 시트가 읽기 전용입니다 |

시험 실행 뒤 실제로 나간 메일은 0통이었고, 진짜 실행 뒤에는 3통이었습니다. 보고서에 오른 단계는 5개 가운데 3개였습니다. 4단계는 시험 실행에서 메일 번호가 만들어지지 않아 조건이 맞지 않았고, 5단계는 시험 실행을 지원하지 않아 아무 말이 없었습니다. 보고서만 읽은 사람은 시트 갱신이 있다는 사실도, 그 단계가 실패할 수 있다는 사실도 알 수 없습니다. 메일 번호가 진짜 실행에서야 생긴 점은 쿠버네티스 문서가 경고한 생성 값의 차이와 같은 모양입니다.

이 시험은 문서의 규칙을 코드로 옮긴 것이어서 결과는 처음부터 정해져 있었고, 새로 알아낸 사실이 아닙니다. 보고서에서 빠지는 자리가 어디인지 눈으로 보려고 한 것입니다. 실제 도구가 이런 단계를 어떻게 보고하는지는 도구마다 다르고 이 글에서 시험하지 않았습니다.

## 시험 실행 중에도 진짜로 일어나는 일이 있습니까?

있습니다. 두 가지가 눈에 띄었습니다.

첫째는 일부러 그렇게 해 둔 단계입니다. Ansible 문서는 단계에 `check_mode: false`를 주면 검사 모드로 돌려도 그 단계는 실제로 시스템을 바꾼다고 설명하고, 예시 단계의 이름을 "항상 시스템을 바꾸는 단계"라고 붙였습니다. 반대로 `check_mode: true`를 주면 평소에도 바꾸지 않고 도는 단계가 됩니다. 시험 실행 스위치를 켰다고 모든 단계가 조용해지는 것은 아니므로, 도구에 이런 고정 설정이 있는지 켜기 전에 확인해야 합니다.

둘째는 읽는 일입니다. 모의 자동화의 1단계는 시험 실행에서도 명단을 실제로 읽었습니다. 읽기는 바깥을 바꾸지 않지만 개인정보가 든 명단을 불러옵니다. 문서에도 비슷한 주의가 있습니다. Ansible의 `--diff` 옵션은 민감한 정보를 드러낼 수 있어서 단계마다 `diff: false`로 끌 수 있다고 안내합니다. 시험 실행 보고서도 보관하고 공유하는 순간부터 자료가 됩니다.

쿠버네티스는 반대 방향으로 조심합니다. 시험 실행이 아닌 실제 요청이었다면 부작용을 일으킬 승인 단계가 끼어 있을 때, 위험을 감수하는 대신 요청을 실패시킵니다. 그래서 시험 실행이 실패했다고 설정이 틀렸다고 단정할 필요는 없습니다. 도구가 위험을 피하려고 일부러 막은 경우도 있습니다.

## AI 단계가 낀 자동화는 시험 실행을 어떻게 읽습니까?

세 문서 어디에도 AI 단계 이야기는 없습니다. 이 절은 문서에서 이끌어 낸 가정이며 시험하지 않았습니다.

- 보고서에 문구를 만들 예정이라고 적혀 있어도 그 문구가 맞는지는 알려 주지 않습니다. 보고되는 것은 단계가 실행될 예정이라는 사실이지 결과물의 품질이 아닙니다.
- 시험 실행에서 모델을 실제로 부르는지 건너뛰는지는 도구마다 다를 수 있습니다. 호출에 비용이 드는 도구라면 시험 실행에서도 비용이 날 수 있으므로, 도구 설명서에서 확인할 칸으로 남겨 둡니다.
- AI 단계의 출력은 시험 실행과 별개로 사람이 샘플 한두 개를 읽어 봐야 합니다. 누가 읽을지 정하는 방법은 [AI 결과 검수자 정하기](/works/ai-output-reviewer-card)에 적었습니다.

## 시험 실행 카드에는 무엇을 적습니까?

도구가 무엇을 보여 주고 무엇을 빠뜨리는지, 켜기 전과 켠 뒤에 누가 무엇을 읽는지를 한 장에 적습니다. 아래 다섯 칸은 위에서 읽은 문서 내용을 작은 사무실이 채울 수 있는 크기로 줄인 것으로, DMS.Labs의 제안입니다. 고객 프로젝트에서 검증한 양식이 아닙니다.

| 칸 | 적을 것 |
|---|---|
| 시험 실행 방법 | 도구의 시험 실행 기능 이름과 켜는 방법, 설명서가 밝힌 확인 범위(권한만인지, 단계 전체인지, 변경 목록인지) |
| 보고되는 단계 | 보고서에 나오는 단계와 안 나오는 단계. 안 나오는 단계는 지원하지 않는 단계와 앞 결과에 따라 갈리는 단계로 나눕니다 |
| 진짜로 실행되는 단계 | 시험 실행 중에도 읽거나 실행하는 단계, 고정 설정이 있는 단계, 개인정보를 불러오는 단계 |
| 켜기 전에 읽을 사람 | 보고서를 읽고 켜도 된다고 말할 사람 한 명, AI 단계의 샘플 출력을 읽을 사람 |
| 켠 뒤에 다시 읽을 것 | 첫 실제 실행이 끝난 뒤 바깥에서 바뀐 것을 어떻게 다시 읽을지 |

직원 여섯 명인 학원이 대기 명단 안내 메일을 자동화한다고 가정해 보겠습니다. 실제 고객 사례가 아닙니다. 이 학원이 카드를 채우다 보면 외부 시트 갱신이 시험 실행 보고서에 나오지 않는다는 점이 켜기 전에 눈에 들어옵니다. 시트 단계는 시험 실행과 별개로 읽기 전용 권한이 아닌지 미리 확인하면 됩니다.

카드의 마지막 칸은 다른 글과 이어집니다. 켠 뒤에 바깥에서 바뀐 것을 다시 읽는 방법은 [성공 출력 뒤에 다시 읽기](/works/read-back-after-success)에 있습니다. 실제 실행 중간에 멈췄을 때 다시 시작해도 되는지는 [AI 자동화 재시작 기준](/works/ai-automation-safe-retry)에서 다뤘습니다. 쓰는 권한을 단계별로 여는 방법은 [AI 자동화, 권한을 세 단계로 나눠 주기](/works/automation-permission-ladder)에 있고, 시험 실행은 그 단계를 올리기 전에 거치는 확인 중 하나로 넣을 수 있습니다.

## 이 글이 확인하지 못한 것은 무엇입니까?

여러 가지가 있습니다. 읽은 세 도구는 서버와 클라우드를 다루는 도구입니다. n8n, Make, Zapier 같은 업무 자동화 도구의 시험 실행이 같은 방식인지는 확인하지 못했습니다. 문서는 Ansible의 검사 모드 문서, 쿠버네티스 API 개념 문서의 시험 실행 절, AWS CLI 문서의 `--dry-run` 옵션 설명을 읽었고 그 밖의 서비스가 시험 실행을 어떻게 다루는지는 읽지 못했습니다. AWS 쪽 근거는 옵션 설명 한 문장입니다.

모의 자동화는 문서의 두 경우를 코드로 옮긴 것이며 실제 도구의 동작을 시험한 것이 아닙니다. AI 단계에 관한 절은 가정입니다. 카드가 사고를 줄인다는 측정도 없습니다. 문서의 내용은 2026년 11월 21일 기준이며 바뀔 수 있습니다.
