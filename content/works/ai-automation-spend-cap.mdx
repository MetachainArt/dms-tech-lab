AI 자동화의 월 비용 상한은 두 개를 따로 정합니다. 넘으면 알려 주기만 하는 알림 한도와, 넘으면 요청을 거부하는 차단 한도입니다. 알림만 걸어 둔 자동화는 잘못 돌아도 계속 돌고, 차단만 걸어 둔 자동화는 멈춘 사실을 아무도 모른 채 며칠을 보내기 쉽습니다. 이 글은 두 한도의 차이, 차단에 걸렸을 때 자동화가 받는 신호, 금액을 정하는 순서를 다룹니다.

이 글은 업무 자동화 운영을 위한 실무 가이드이며, 특정 고객사의 도입 사례나 측정 결과가 아닙니다. 2026년 11월 1일 확인한 OpenAI와 Anthropic의 공식 문서 기준입니다. 한도 금액, 오류 이름, 설정 화면의 위치는 바뀔 수 있습니다. 아래의 한 장짜리 상한 카드와 가상의 여행 상담 업체 예시는 DMS.Labs의 설계 제안이며, 조직의 예산 규정이나 계약을 대신하지 않습니다. 이 글은 가격을 다루지 않습니다. 모델별 단가는 사용하는 곳의 공식 가격표에서 확인하십시오.

## 알림만 걸어 두면 자동화가 폭주해도 멈춥니까?

멈추지 않습니다. OpenAI 문서에 따르면 지출 알림(spend alert)은 알림을 보낼 뿐이고 API 트래픽은 그대로 이어집니다. 요청을 막는 것은 하드 한도(hard spend limit)입니다. 조직이나 프로젝트에 월 상한을 정한 뒤 'Enforce a hard limit'를 켜야 작동합니다. 프로젝트 한도를 만들면 한도의 100% 지점에 알림이 기본으로 하나 생기고, 다른 비율의 알림은 따로 추가합니다.

알림의 쓸모는 사람이 보고 판단할 시간을 버는 것입니다. 알림이 메일함에 쌓이기만 하고 읽는 사람이 없는 주말이라면 비용은 줄지 않습니다. 알림을 받을 사람과 그 사람이 쉬는 날의 대리인은 [자동화 담당자 카드](/works/automation-owner-card)와 같은 방식으로 미리 적어 둬야 합니다.

## 차단 한도에 걸리면 자동화는 어떤 신호를 받습니까?

신호는 제공자와 설정 위치마다 다릅니다. 두 회사의 문서에서 읽은 내용을 한 표에 모았습니다.

| 한도 | 넘었을 때 | 자동화가 받는 응답 | 문서에 적힌 풀이 방법 |
| --- | --- | --- | --- |
| OpenAI 지출 알림 | 알림만 가고 요청은 계속됩니다 | 오류 없음 | 해당 없음 |
| OpenAI 조직 하드 한도 | 조직 전체 요청이 거부됩니다 | HTTP 429, 코드 organization_spend_limit_exceeded | 한도를 올리거나 해제합니다. 그대로 두면 다음 달 주기에 초기화됩니다 |
| OpenAI 프로젝트 하드 한도 | 그 프로젝트로 청구되는 요청만 거부됩니다 | HTTP 429, 코드 project_spend_limit_exceeded | 위와 같습니다 |
| Anthropic 등급별 월 상한 | 다음 달 1일 00:00 UTC까지 사용이 멈춥니다 | HTTP 429, 오류 유형 rate_limit_error, 코드 enforced_spend_limit_reached, retry-after 없음 | 상한 상향을 요청합니다 |
| Anthropic에서 직접 정한 한도 | 요청이 거부됩니다 | HTTP 400, 오류 유형 invalid_request_error | 한도를 올리거나 제거합니다 |
| 속도 제한(분당 요청·토큰) | 잠시 거부됩니다 | HTTP 429, retry-after 헤더가 있으면 그 시간만큼 대기 | 안내된 시간 뒤 다시 보냅니다 |

Anthropic 문서는 등급별 월 상한을 Start 500달러, Build 1,000달러, Scale 20만 달러로 적고, Custom 등급에는 월 상한이 없다고 합니다. 2026년 11월 1일에 읽은 값입니다. Claude Code 워크스페이스는 따로 검사되어 retry-after가 붙은 429가 올 수 있다는 설명도 있습니다.

표에서 눈여겨볼 곳은 429입니다. 같은 숫자인데 어떤 429는 몇 초 기다리면 풀리고, 어떤 429는 다음 달 1일이나 사람의 조치가 있어야 풀립니다. 자동화가 숫자만 보고 움직이면 둘을 구별하지 못합니다. 오류 코드까지 읽어야 합니다.

## 한도 오류를 받으면 다시 시도해도 됩니까?

월 한도에 걸린 요청은 다시 보내도 통과하지 않습니다. Anthropic 문서는 상한 도달 429에 retry-after 헤더가 없고, SDK의 자동 재시도를 포함해 접근이 다시 열릴 때까지 실패한다고 적습니다. OpenAI 도움말도 이 오류들은 재시도로 풀리지 않고 크레딧이나 한도를 바로잡아야 풀린다고 말합니다.

자동화 도구가 '실패하면 잠시 뒤 다시'를 기본값으로 쓴다면 문제가 될 수 있습니다. 이 글은 도구별 기본 재시도 설정을 확인하지 않았습니다. 쓰고 있는 도구의 설정은 직접 열어 보십시오.

DMS.Labs는 오류를 두 갈래로 나눠 둘 것을 제안합니다. 기다리면 풀리는 오류(속도 제한)와 사람이 풀어야 하는 오류(한도, 크레딧)입니다. 두 번째를 받으면 자동화는 남은 대상을 처리하지 않고 멈춥니다. 어디까지 처리했는지는 [실행 기록](/works/automation-run-record)에 '일부만 완료'로 남기고, 담당자에게 알립니다. 한도를 올린 뒤 이어서 돌릴 때는 [재시작 기준](/works/ai-automation-safe-retry)에서 말한 대로 이미 나간 결과부터 확인합니다.

## 한도 금액은 어떻게 정합니까?

정확한 금액을 맞히려 하기보다 '이 자동화가 한 달에 여기까지 써도 잘못은 아니다'라는 선을 먼저 합의합니다. 아래 순서는 DMS.Labs의 제안입니다.

1. 시험 기간의 실제 사용량을 봅니다. OpenAI와 Anthropic 모두 관리 화면에 사용량 페이지가 있습니다. Anthropic Messages API의 응답에는 사용한 입력 토큰과 출력 토큰이 usage 항목으로 담겨 옵니다. 실행마다 이 값을 기록하면 한 번의 실행이 얼마나 쓰는지 알 수 있습니다.
2. 실행 한 번이 모델을 몇 번 부르는지 셉니다. Anthropic 문서는 Messages API가 상태를 저장하지 않아서 매 호출에 대화 내용 전체를 보내야 한다고 설명합니다. 여러 단계로 도는 자동화는 단계가 늘수록 보내는 입력도 늘어난다고 DMS.Labs는 해석합니다. 문서가 적은 것은 상태를 저장하지 않는다는 데까지입니다.
3. 감당할 수 있는 손실액을 정합니다. 이 금액을 차단 한도의 위쪽 끝으로 봅니다.
4. 차단 한도는 그 금액보다 낮게 잡습니다. OpenAI 문서는 한도 집행이 즉시 이뤄지지 않아 기록된 지출이 한도를 조금 넘을 수 있다고 적습니다. 알림은 차단 한도 아래에 한두 개 더 둡니다. 예를 들어 절반과 80% 지점입니다. 이 비율은 예시이며 정해진 기준이 아닙니다.
5. 매달 첫 주에 사용량과 한도를 함께 읽고, 올리거나 내린 이유를 한 줄 남깁니다.

## 한도는 어디에 걸어야 다른 자동화가 같이 멈추지 않습니까?

자동화마다 비용이 청구되는 곳을 나눠 두면 한 자동화가 한도에 걸려도 나머지는 계속 돕니다. OpenAI에서는 조직 한도가 모든 프로젝트의 트래픽에 적용되고, 프로젝트 한도는 그 프로젝트로 청구되는 트래픽에만 적용됩니다. Anthropic은 워크스페이스마다 지출·속도 한도를 따로 정할 수 있고, 조직 전체 한도는 워크스페이스 한도 합과 상관없이 늘 적용됩니다. 기본 워크스페이스에는 지출 한도를 걸 수 없다는 제약이 문서에 적혀 있습니다.

이를 사무실 규모로 옮기면 DMS.Labs는 이렇게 제안합니다. 자동화 하나에 프로젝트나 워크스페이스 하나를 따로 배정하고, 그 이름을 담당자 카드의 이름과 맞춥니다. 같은 키를 여러 자동화가 나눠 쓰고 있다면 한도가 걸린 날 어느 자동화가 원인이었는지 가리기 어렵습니다. 이 구성이 실제로 얼마나 관리 부담을 줄이는지는 측정한 적이 없습니다.

## 가상의 여행 상담 업체에서 계산해 보면

직원 여덟 명쯤 되는 가상의 여행 상담 업체를 가정합니다. 실제 고객이나 현장의 기록이 아닙니다. 자동화는 하나입니다. 상담 문의 메일을 읽어 분류하고, 답장 초안을 만들어 담당자에게 넘깁니다. 하루 문의는 40건이고, 한 건을 처리하는 데 모델 호출이 세 번 든다고 가정합니다. 정상일 때 하루 호출은 120번입니다.

어느 날 처리에 실패한 문의 40건을 1분마다 다시 처리하도록 잘못 설정되었다고 가정합니다. 40건에 60분, 24시간을 곱하면 하루 57,600번이고, 정상의 480배입니다. 알림만 걸려 있다면 알림은 오지만 읽는 사람이 나타날 때까지 호출이 계속됩니다. 차단 한도가 걸려 있으면 한도에 닿은 뒤 요청이 거부되기 시작합니다. 그런데 이 자동화가 회사의 다른 자동화와 같은 프로젝트를 쓰고 있었다면, 다른 일도 한도가 풀릴 때까지 같이 멈춥니다.

그래서 이 업체는 문의 분류 자동화에 전용 프로젝트를 주고, 절반과 80% 지점에 알림을, 감당할 수 있는 금액보다 낮은 곳에 차단 한도를 겁니다. 한도에 걸리면 자동화가 남은 문의를 건드리지 않고 멈춰서 담당자에게 알리도록 합니다. 이 계산은 가정입니다. 실제 호출 단가, 도구의 재시도 설정, 한 번의 호출에 드는 금액은 다루지 않았습니다.

## 상한 카드에는 어떤 칸이 들어갑니까?

자동화마다 아래 칸을 한 줄로 적습니다. 담당자 카드, 실행 기록과 같은 표 옆에 두면 한눈에 이어집니다. 이 칸 구성은 DMS.Labs의 제안입니다.

| 칸 | 적는 내용 | 비어 있으면 생기는 일 |
| --- | --- | --- |
| 자동화 이름 | 담당자 카드의 이름 그대로 | 한도에 걸린 날 어느 자동화인지 찾아야 합니다 |
| 비용이 청구되는 곳 | 조직, 프로젝트, 워크스페이스 이름. 키 값은 적지 않습니다 | 한도를 어디에 걸었는지 알지 못합니다 |
| 알림 지점 | 월 한도 대비 몇 % 지점에서 알리는지 | 알림이 한 번도 오지 않은 채 차단됩니다 |
| 차단 한도와 켠 여부 | 금액은 조직이 정한 값. 하드 한도를 켰는지 | 알림만 있는 줄 알고 있다가 폭주를 못 막습니다 |
| 걸렸을 때 자동화의 동작 | 남은 대상 처리 중단, 실행 기록에 남기기, 알림 | 같은 요청을 계속 다시 보냅니다 |
| 알림 받는 사람과 대리인 | 이름과 연락 방법 | 휴일에 아무도 알지 못합니다 |
| 한도를 올릴 수 있는 사람 | 이름과 올리기 전 확인할 것 | 급한 마음에 한도만 풀어 버립니다 |

한도를 올리기 전에 확인할 것은 하나입니다. 늘어난 사용이 정상적인 증가인지 반복 호출 때문인지를 실행 기록에서 먼저 봅니다. 반복 호출이 원인이라면 한도를 올리는 것은 문제를 키울 뿐입니다.

## 자주 묻는 질문

### 구독형 앱 요금제에도 같은 상한이 있습니까?

이 글은 API 사용 기준입니다. 구독형 ChatGPT나 Claude 앱의 사용량 한도는 확인하지 않았습니다. 요금제와 계정에 따라 다르므로 해당 서비스의 도움말에서 확인하십시오.

### 한도를 올리면 바로 다시 돌아갑니까?

OpenAI 문서는 올리거나 제거한 한도가 반영된 뒤에 트래픽이 재개된다고 적습니다. Anthropic 문서는 한도를 올리거나 제거하면 접근을 더 일찍 되찾을 수 있다고 합니다. 반영에 걸리는 시간은 확인하지 않았습니다. 재개하기 전에 멈춘 실행이 어디까지 갔는지부터 보십시오.

### 한도를 낮게 잡으면 일이 자주 멈추지 않습니까?

멈춥니다. OpenAI 문서도 하드 한도가 운영 중인 트래픽을 끊을 수 있다고 경고합니다. 그래서 멈춰도 사람이 대신 처리할 수 있는 일인지를 기준으로 자동화마다 따로 정하십시오. 고객에게 바로 나가는 일일수록 멈췄을 때 누가 이어받을지를 먼저 정해 둡니다. 이 기준은 DMS.Labs의 제안입니다.
