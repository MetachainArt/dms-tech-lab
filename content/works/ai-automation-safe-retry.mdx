AI 자동화가 멈췄다고 처음부터 다시 실행하면 이미 끝난 일을 중복 처리할 수 있습니다. 재시도하기 전에 외부 시스템의 결과를 확인하고, 완료가 확인된 단계는 건너뛰어야 합니다. 결과가 불명확한 발송·등록 작업은 보류한 뒤 담당자가 확인하는 편이 안전합니다.

이 글은 AWS의 멱등성 문서와 DMS.Labs의 기존 업무 설명서·권한 단계 가이드를 연결한 실무 설계안입니다. 특정 고객의 구축 성과를 보고하거나 아래 절차를 모든 도구에서 시험했다는 뜻은 아닙니다. 문서 등록 상황은 설명을 위한 가정이며, 공식 자료는 2026년 10월 13일 확인했습니다.

## 시간초과가 나면 일이 안 된 걸까요?

응답을 받지 못했다는 사실만으로 작업이 실행되지 않았다고 판단할 수는 없습니다. 요청을 받은 시스템은 처리를 마쳤는데 응답만 돌아오지 않았을 가능성이 있습니다. 반대로 요청 자체가 도착하지 않았을 수도 있습니다. 자동화 화면의 오류 메시지는 이 두 상황을 구분해 주지 못합니다.

AWS Builders’ Library는 가상의 EC2 인스턴스 생성 요청을 예로 설명합니다. 요청 후 네트워크 시간초과가 나면 호출한 쪽은 인스턴스가 실행 중인지 알기 어렵고, 바로 재시도하면 여러 인스턴스가 생길 위험이 있습니다. 이때 실제 상태를 대조하는 일이 필요합니다. 같은 원리를 문서 등록에 적용하면 등록 버튼을 누른 뒤 화면이 멈췄을 때 먼저 목록과 문서 식별자를 확인하는 순서가 됩니다.

AI가 오류 메시지를 읽고 다음 행동을 고르는 자동화에서도 이 구분이 필요합니다. 모델이 실패라고 요약한 문장은 외부 시스템의 처리 결과를 증명하지 않습니다. 원래 요청의 기록과 상대 시스템에 남은 결과를 연결해 확인해야 합니다. 단순 조회를 다시 하는 일과, 새 문서를 만드는 일을 같은 재시도 규칙으로 묶으면 이 차이를 놓치기 쉽습니다.

## 완료 여부를 네 칸으로 나눕니다

DMS.Labs는 이 가이드에서 업무를 미시도, 진행 중, 완료 확인, 결과 불명으로 구분하도록 제안합니다. 도구 화면에 적힌 성공·실패만 옮기는 대신, 그 상태를 뒷받침하는 근거와 다음 행동을 함께 적습니다. 아래 표는 이 글의 설계 예시이며 산업 표준이나 제품의 기본 기능이 아닙니다.

| 상태 | 확인할 근거 | 다음 행동 |
| --- | --- | --- |
| 미시도 | 요청을 보내지 않은 기록 | 기존 승인 범위에서 실행 |
| 진행 중 | 처리 중인 작업 식별자 | 상태 조회, 새 요청 보류 |
| 완료 확인 | 상대 시스템의 결과 식별자와 내용 | 해당 단계 건너뛰기 |
| 결과 불명 | 시간초과 또는 서로 맞지 않는 기록 | 읽기 전용 대조 후 사람 확인 |

상태는 업무 단계마다 붙입니다. 초안 작성이 끝났고 등록 결과가 불명확하다면, 작성까지 전부 실패로 돌리지 않습니다. 승인된 초안은 보존하고 등록 결과를 먼저 확인합니다. 완료 확인에는 정확한 대상 계정과 문서 내용도 포함해야 합니다. 문서가 있다는 이유만으로 다른 계정에 잘못 올린 결과를 성공 처리해서는 안 됩니다.

진행 중에는 이전 요청이 아직 살아 있는지도 살핍니다. 화면을 닫았거나 AI의 설명이 끊겨도 뒤에서 실행하던 작업이 끝났다고 단정할 수 없습니다. 확인할 방법이 없으면 상태를 결과 불명으로 옮기고, 외부에 새 결과를 만드는 행동을 보류합니다. 이 보류 조건은 업무 설명서에 미리 적어 두는 편이 좋습니다.

## 같은 요청을 알아볼 표식이 필요합니다

멱등성은 같은 요청을 여러 번 보내더라도 추가 부작용이 생기지 않는 성질입니다. AWS 문서는 호출자가 고유한 요청 식별자를 보내고, 서비스가 같은 호출자의 같은 식별자를 중복 요청으로 알아보는 방식을 설명합니다. 내용이 똑같다는 이유만으로 중복을 판정하면, 사용자가 동일한 자원을 두 개 만들려는 의도를 잘못 해석할 수 있다는 지적도 담겨 있습니다.

따라서 업무 담당자는 같은 일을 다시 시도하는 것인지, 같은 내용의 새 일을 만드는 것인지 구분해야 합니다. 설명을 위한 예로 월간 보고서 등록 작업에 업무 식별자를 붙였다고 가정해 보겠습니다. 같은 승인본의 등록 재시도에는 기존 식별자를 유지합니다. 새 승인본을 따로 등록해야 한다면 그 의도를 별도 작업으로 기록합니다. 파일 이름이 같다는 사실만으로 둘을 합치지 않습니다.

메모장에 식별자를 적는 것만으로 서버의 중복 방지가 구현되지는 않습니다. AWS는 요청 표식을 기록하는 작업과 실제 변경 작업이 원자적으로 처리돼야 한다고 설명합니다. 원자적이라는 말은 둘 다 반영되거나 둘 다 반영되지 않아야 한다는 뜻입니다. 표식만 남고 결과가 없거나, 결과는 생겼는데 표식이 없으면 다음 시도에서 잘못 판단할 수 있습니다.

사용하는 서비스가 멱등성 키를 지원한다면 적용 범위와 유효 조건을 공식 문서에서 확인해야 합니다. 지원하지 않는 화면 자동화라면 결과 목록 대조와 담당자 확인으로 위험을 줄일 수는 있지만, 같은 수준으로 중복을 막는다고 보장할 수 없습니다. 동시에 여러 실행이 시작되는 경우까지 고려해야 하므로, 단순한 로컬 파일 존재 검사를 안전장치 전체로 삼지 않는 편이 좋습니다.

## 재시도할 때 승인은 어디까지 이어질까요?

같은 승인 대상과 범위 안에서 복구하는지 먼저 확인합니다. 한 문서의 등록을 승인받았다고 해서 새 문서 여러 개를 만들거나 다른 계정으로 옮길 권한이 생기는 것은 아닙니다. 초안 내용이나 수신 대상이 바뀌면 원래 승인이 그 변경을 포함하는지 확인해야 합니다. 이 기준은 [읽기·초안·실행으로 권한을 나누는 가이드](/works/automation-permission-ladder)의 구분을 재시도 상황에 적용한 것입니다.

복구 규칙에는 어느 단계부터 이어갈지와 언제 멈출지를 같이 적습니다. 예를 들어 초안과 승인 기록이 남아 있고 등록이 아직 시작되지 않았다는 근거가 있으면 등록 단계부터 이어갈 수 있습니다. 이미 등록된 결과를 찾았다면 그 결과를 검수하고 새 등록은 하지 않습니다. 근거가 서로 다르면 재시도 횟수를 늘리기 전에 불일치부터 확인합니다.

기다리는 간격과 최대 시도 횟수는 해당 서비스의 제한, 업무 마감, 사람이 대응할 시간을 보고 정합니다. 모든 업무에 맞는 횟수를 이 글에서 제시하지 않습니다. 권한 오류나 잘못된 입력은 기다린다고 해결되지 않을 수 있으므로 같은 요청을 반복하기보다 원인을 수정해야 합니다. 외부 기록을 바꾸지 않는 조회와, 외부에 새 결과를 만드는 실행의 한도를 따로 두면 운영자가 판단하기 쉽습니다.

## DMS 업무 설명서에 무엇을 덧붙이면 될까요?

기존 여섯 칸 업무 설명서의 완료 기준과 실패 시 행동에, 외부 결과를 확인할 위치와 재시작 지점을 덧붙이면 됩니다. [업무 설명서 한 장 가이드](/works/ai-skill-job-sheet)는 목적과 입력, 결과 형식, 완료 기준, 금지 사항, 실패 시 행동을 정리합니다. 여기에 별도 양식을 늘리기보다 문서 등록 업무의 완료 기준을 구체적으로 적는 방법을 권합니다.

완료 기준에는 등록된 문서의 주소, 대상 계정, 승인된 내용과의 일치 여부를 적습니다. 실패 시 행동에는 시간초과가 나면 결과 목록을 먼저 조회하고, 이미 확인된 결과는 다시 만들지 않으며, 확인이 안 되면 담당자에게 넘긴다고 적습니다. 담당자가 보게 될 기록에는 원래 업무 식별자와 마지막으로 확인한 단계가 있어야 합니다. 비밀번호나 접근 토큰을 복구 메모에 넣지는 않습니다.

교육 실습에서는 실제 외부 발송이나 고객 문서 등록 대신 시험용 자료와 허용된 환경을 씁니다. 설명용 시험 항목으로는 완료 뒤 응답만 끊긴 경우, 같은 일을 두 번 시작하려는 경우, 완료 기록과 실제 결과가 맞지 않는 경우를 둘 수 있습니다. 이 글에서 직접 실행한 시험 결과는 아닙니다. 각 상황에서 새 결과를 만들지 않고 멈추거나 이어갈 위치를 설명할 수 있는지 확인하는 데 목적이 있습니다.

담당자가 수동으로 일을 마친 경우에는 그 결과를 기존 업무 식별자에 연결하고 완료 확인으로 남깁니다. 자동화가 나중에 돌아왔을 때 같은 일을 새로 시작하지 않도록 하기 위한 기록입니다. 해결되지 않은 항목은 미완료로 표시하고, 확인 방법과 맡을 사람을 적습니다. 보류를 실패 통계에서 숨기면 운영자는 실제 남은 일을 알기 어렵습니다.

복구 기록은 결과를 확인하는 사람이 실제로 찾아갈 수 있어야 합니다. 성공이라는 표시만 남기는 대신 결과 주소와 확인 시각, 다음에 조회할 위치를 연결합니다. 내용 전체를 복사해 두기보다 필요한 식별 정보만 남기면 민감한 자료가 불필요하게 퍼지는 일도 줄일 수 있습니다. 기록을 어디까지 보관하고 누가 볼 수 있는지는 업무의 개인정보·보안 조건에 맞춰 정해야 합니다.

재시작 직전에는 현재 계정과 권한도 다시 확인합니다. 처음 요청할 때의 계정으로 접속돼 있는지, 같은 대상에 변경을 할 수 있는지 살핍니다. 로그인 창이 나타났다는 이유로 다른 계정을 골라 일을 이어가면 원래 승인 범위를 벗어날 수 있습니다. 접근 권한이 없어 결과를 확인하지 못했다면 완료 여부를 추측하지 않고 그 제한을 담당자에게 남깁니다.
