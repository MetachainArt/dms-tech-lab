자동화가 쓰는 API 키는 새 키를 먼저 만들어 자동화에 연결하고, 새 키로 호출이 한 번 성공하는 것을 확인한 뒤에 옛 키를 폐기하는 순서로 바꿉니다. 이 순서가 뒤집히면 옛 키가 막힌 시각부터 새 키가 연결될 때까지 자동화가 멈춥니다. 키가 밖으로 새어 나간 것으로 의심될 때만 순서를 바꿔 옛 키 폐기를 먼저 합니다.

2026년 11월 17일 확인한 공식 자료(OpenAI 도움말, OWASP 비밀 관리 치트시트, GitHub Docs)와 내 컴퓨터에서 돌린 모의 서버 시험 기준입니다. 고객사 프로젝트 사례가 아니며, 아래 카드가 사고를 줄인다는 측정은 이 글에 없습니다.

## 키를 바꾸는 날, 왜 자동화가 멈춥니까?

키를 바꾸는 일이 서로 다른 두 곳을 맞추는 일이기 때문입니다. 한 곳은 서비스 쪽의 키 목록이고, 다른 한 곳은 자동화가 매번 읽어 가는 저장 위치(환경 변수나 도구의 자격 증명 칸)입니다. 두 곳은 따로 움직입니다. 순서를 잘못 잡으면 둘이 어긋나 있는 동안의 호출이 모두 거절됩니다.

[OpenAI의 API 키 안전 도움말](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety)은 이 순서를 직접 적어 두었습니다. 키가 만료되기 전에 교체용 키를 만들고, 애플리케이션이 그 키를 쓰도록 바꾸고, 교체한 키가 동작하는 것을 확인한 뒤에 옛 키를 폐기하라는 내용입니다. 같은 문서는 프로젝트 키를 만들 때 만료일을 두라고 권하고, 만료일이 지나면 그 키의 요청은 거절된다고 설명합니다. 관리자는 조직이나 프로젝트 단위로 키의 최대 유효 기간을 정할 수도 있다고 합니다.

리도의 글 자동화 기록에도 키 문제로 보이는 날이 한 번 있습니다. 11월 2일 회차는 모델 키 오류로 중간에 끊겼고, 그 차례였던 글을 11월 3일에 올려 복구했습니다. 다만 기록에는 오류의 이름만 남아 있습니다. 키를 바꾸던 중이었는지, 만료였는지, 설정 오류였는지는 적혀 있지 않아서 이 글은 원인을 짐작하지 않습니다.

## 어떤 순서로 바꿔야 합니까?

새 키 발급, 연결 교체, 새 키로 호출 확인, 옛 키 폐기의 네 단계입니다. 옛 키는 마지막까지 살려 두기 때문에 어느 단계에서든 자동화가 쓸 수 있는 키가 하나는 있습니다.

| 단계 | 하는 일 | 이 시점에 자동화가 쓰는 키 |
|---|---|---|
| 1 | 서비스에서 새 키를 발급합니다 | 옛 키(아직 유효) |
| 2 | 자동화의 저장 위치를 새 키로 바꿉니다 | 새 키 |
| 3 | 새 키로 호출 한 번이 성공하는지 봅니다 | 새 키 |
| 4 | 서비스에서 옛 키를 폐기합니다 | 새 키 |

순서가 달라지면 결과가 어떻게 달라지는지 내 컴퓨터에서 확인했습니다. Node로 모의 서버를 하나 띄웠습니다. 요청 헤더의 키가 유효한 키 목록에 있으면 200, 없으면 401을 돌려주는 서버입니다. 실제 OpenAI나 다른 서비스의 API가 아니라, 문서가 설명한 규칙을 코드로 옮긴 것입니다. 각 단계마다 자동화 역할을 하는 호출을 한 번씩 보냈습니다.

| 순서 | 호출 결과(단계별) | 실패한 호출 |
|---|---|---|
| A 새 키 먼저(문서의 순서) | 200, 200, 200, 200 | 0번 |
| B 옛 키 먼저 폐기 | 200, 401, 401, 200 | 2번 |

A에서는 옛 키를 폐기한 뒤 옛 키로 다시 호출하면 401이 나왔습니다. 모의 서버에서는 옛 키 폐기가 곧바로 효력을 냈다는 뜻입니다. B에서는 옛 키를 먼저 지운 뒤 자동화의 키를 바꾸기 전까지 두 번의 호출이 거절됐습니다. 규칙을 코드로 옮긴 시험이어서 결과는 처음부터 정해져 있었고, 새로 알아낸 사실은 아닙니다. 순서에 따라 거절이 나는 구간이 어디인지 눈으로 보려고 한 것입니다. 실제 서비스에서 폐기가 반영되기까지 걸리는 시간과, 이미 시작된 긴 작업이 중간에 키를 잃는 경우는 시험하지 않았습니다.

## 키가 비어 있어도 자동화는 돌아갑니까?

돌아갈 수 있습니다. 호출이 그대로 나가고, 서비스가 거절한 뒤에야 실패가 드러납니다.

[GitHub Actions 문서](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)에는 설정하지 않은 secret을 참조하면 오류 대신 빈 문자열이 돌아온다고 적혀 있습니다. 이름을 잘못 쓴 변수도 비슷하게 빈 값이 됩니다. 같은 문서는 secret을 `if:` 조건에서 직접 참조할 수 없고, 필요하면 작업 단계의 환경 변수로 옮겨 그 변수를 조건에 쓰라고 안내합니다. 명령줄 인수로 secret을 넘기면 다른 사용자가 프로세스 목록에서 볼 수 있으므로 환경 변수나 표준 입력을 쓰라는 문장도 있습니다.

모의 서버 시험에서도 같은 일을 확인했습니다. 존재하지 않는 변수 이름으로 키를 읽자 값은 빈 문자열이 됐고, 그 빈 키를 실은 호출은 그대로 나가 401을 받았습니다. 자동화가 받는 것은 401 한 줄이어서 실패의 이유가 '키가 비어 있음'이라고 바로 보이지는 않습니다. 호출 전에 키가 비어 있으면 멈추는 점검을 넣으면 이유가 첫 줄에 적힙니다.

```js
function requireKey(name) {
  const v = process.env[name];
  if (!v) throw new Error(`키 변수 ${name} 가 비어 있습니다. 호출 전에 멈춥니다.`);
  return v;
}
```

이 함수는 오류 문구에 변수 이름만 적고 키 값은 적지 않습니다. 호출을 보내기 전에 멈추므로 키가 비어 있는 날과 키가 거절된 날이 기록에서 구분됩니다. 이 점검은 키가 비어 있는지만 보며 키가 유효한지는 확인하지 못합니다. 만료된 키는 이 점검을 통과해 서비스에서 거절됩니다. [OWASP 비밀 관리 치트시트](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)도 비밀을 쓰는 쪽이 그 비밀이 아직 유효한지 확인한 뒤에 믿어야 한다고 적었습니다. 유효한지는 첫 호출의 결과로 확인하고, 실패하면 알려 주는 길이 있어야 합니다. 알림이 도착하는지 확인하는 방법은 [안 돌아간 날, 누가 압니까](/works/automation-missed-run-check)에서 다뤘습니다.

## 키가 새어 나갔을 때도 같은 순서입니까?

아닙니다. 새어 나간 것이 의심되면 옛 키 폐기가 먼저입니다. 자동화가 잠시 멈추더라도 폐기를 늦출 이유가 없기 때문입니다.

OWASP 치트시트의 사고 대응 절은 순서를 폐기, 교체, 삭제, 기록의 네 단계로 적었습니다. 노출된 키는 즉시 폐기하고, 새 비밀을 만들어 적용하고, 노출된 곳(코드나 로그)에서 폐기된 비밀을 지우고, 누가 접근했고 언제 썼는지 같은 이력을 남깁니다. 코드에 들어간 비밀을 지우려고 깃(Git) 기록을 다시 쓰면 그 커밋을 가리키던 다른 링크가 깨질 수 있다는 주의도 있습니다. 같은 문서의 다른 절은 애플리케이션을 다시 시작해도 훔친 자격 증명이 무효가 되지는 않으며 서비스가 만료시키거나 폐기할 때까지 쓸 수 있다고 설명합니다. 재시작이 대응이 될 수 없다는 뜻입니다.

OpenAI 도움말도 키가 새어 나갔다고 믿을 이유가 있으면 키 목록에서 바로 키를 교체하라고 하고, 사용량 페이지를 열어 평소 업무와 맞는지 보라고 안내합니다. 같은 문서는 월별 사용 한도를 두고 강제 적용을 켜면 키가 유출됐을 때 예상 밖의 비용을 줄이는 데 도움이 된다고 설명하면서, 그 강제가 정상 요청도 막을 수 있다고 적었습니다. 한도를 정하는 방법은 [AI 자동화, 월 비용 상한 정하기](/works/ai-automation-spend-cap)에서 다뤘습니다.

| 상황 | 첫 행동 | 이유 |
|---|---|---|
| 정해 둔 교체일이 됐다 | 새 키를 먼저 만들어 연결합니다 | 어느 시점에도 쓸 수 있는 키가 하나는 남습니다 |
| 유출이 의심된다 | 옛 키를 먼저 폐기합니다 | 막힌 자동화보다 열려 있는 키의 위험이 큽니다 |
| 키를 나눠 쓰던 사람이 떠난다 | 사람마다 따로 받은 키였다면 그 사람 키만 폐기합니다 | 공용 키 하나였다면 모두가 새 키를 받아야 합니다 |

마지막 행의 설명은 문서의 내용을 해석한 것입니다. OpenAI 도움말은 키를 공유하지 말고 팀원마다 자기 키를 받게 하라고 안내합니다. 사람별 키가 서비스마다 같은 방식으로 지원되는지는 이 글에서 확인하지 못했습니다.

## 열쇠 카드에는 무엇을 적습니까?

키 값은 적지 않고, 그 키를 누가 어디에 쓰며 언제 어떤 순서로 바꾸는지를 적습니다. OWASP 치트시트는 비밀을 관리하는 곳이 최소한 언제 만들고 바꾸고 지웠는지, 누가 했는지, 어디에 쓰는지, 문제가 생기면 누구에게 연락하는지, 수동으로 바꾼다면 언제 바꿔야 하는지를 함께 저장해야 한다고 적었습니다. 아래 카드는 그 항목을 작은 사무실이 한 장에 적을 수 있게 줄인 것으로, DMS.Labs의 제안입니다. 고객 프로젝트에서 검증한 양식이 아닙니다.

| 칸 | 적을 것 |
|---|---|
| 이름과 쓰이는 곳 | 키의 이름(값은 적지 않습니다)과 그 키를 쓰는 자동화 이름 |
| 담당과 연락 | 담당 한 명과 연락 방법, 자리를 비울 때 대신 볼 사람 |
| 만료일과 교체일 | 서비스에서 만료일을 정할 수 있으면 그 날짜, 없으면 직접 정한 교체일 |
| 교체 순서 | 새 키 발급, 연결 교체, 새 키로 호출 확인, 옛 키 폐기와 각 단계의 확인 방법 |
| 유출이 의심될 때 | 옛 키 폐기, 새 키 발급, 사용량 확인, 알릴 사람 |

직원 6명인 학원이 수강 문의 답변 초안을 만드는 자동화 하나에 AI 서비스 키 하나를 쓴다고 가정해 보겠습니다. 가정이므로 실제 고객 사례가 아닙니다. 이 학원이 원장과 강사 둘이 같은 키를 나눠 쓰고 있었다면, 카드를 쓰는 과정에서 먼저 드러나는 것은 사용자마다 키를 나누는 일이 필요하다는 점입니다. 자동화마다 프로젝트나 키를 따로 두면 한도에 걸린 날 어느 자동화 때문인지 가릴 수 있다는 점도 앞서 비용 상한 글에서 다뤘습니다. 담당자를 정하는 칸은 [자동화를 만든 사람이 없는 날](/works/automation-owner-card)의 카드와 이어 쓰면 됩니다. 교체일은 예를 들어 90일 뒤로 달력에 같이 적어 둘 수 있습니다. 90일은 예시이며 근거가 있는 권장 기간이 아닙니다.

## 이 글이 확인하지 못한 것은 무엇입니까?

순서 시험은 모의 서버에서만 돌렸습니다. 실제 서비스가 옛 키 폐기를 얼마나 빨리 반영하는지, 폐기 직전에 보낸 요청이 어떻게 처리되는지는 시험하지 않았습니다. 읽은 문서는 OpenAI 도움말과 GitHub Docs의 해당 페이지 전체, OWASP 치트시트의 필요한 절입니다. Anthropic이나 n8n 같은 다른 서비스와 도구가 키를 어떻게 다루는지는 읽지 못했습니다. 키 만료일 설정과 관리자의 최대 유효 기간, 사람별 키 발급이 계정 종류에 따라 다른지도 확인하지 못했습니다.

OpenAI 도움말에는 수명이 긴 키 대신 짧게 쓰는 접근 토큰을 받는 방식(workload identity federation)과 허용한 IP 주소에서 온 요청만 받는 설정도 나옵니다. 읽기만 했고 해 본 일은 아닙니다. 11월 2일 모델 키 오류의 원인도 모릅니다. 열쇠 카드가 사고를 줄인다는 측정도 없습니다.

문서의 내용은 2026년 11월 17일 시점이며 바뀔 수 있습니다.
