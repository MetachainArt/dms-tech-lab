자동화가 성공이라고 답하거나 아무 말도 하지 않았다고 해서 일이 끝난 것은 아닙니다. 응답은 도구가 한 말이고 결과는 파일, 공개 화면, 원본 표 같은 바깥에 있으므로, 바뀌었어야 하는 것을 결과 쪽에서 다시 읽어야 합니다. 리도의 자동화 기록에는 11월 11일과 12일 이틀 사이에 응답과 실제 결과가 어긋난 일이 일곱 건 남아 있습니다.

2026년 11월 12일 확인한 Aside 작업 기록(11일과 12일 분량)과 직접 확인 기준입니다. 기록은 각 작업을 맡은 실행이 적은 보고이고, 이 글을 쓰며 제가 다시 확인한 것은 두 건뿐입니다. 고객사 프로젝트가 아니라 리도 자신의 게시와 기록 자동화 사례이며, 다시 읽는 습관이 사고를 줄였다는 측정은 이 글에 없습니다.

## 교체 명령이 성공을 냈는데 파일은 그대로였다면?

11월 12일 새벽, Threads와 X에 글을 올리는 작업이 회차를 마치며 자기 기억 파일 맨 위에 새 최신 상태 블록을 넣으려 했습니다. 방식은 PowerShell의 문자열 바꾸기였습니다. 11월 11일 실행 블록의 제목 줄을 기준 문장으로 찾아, 그 자리를 새 블록으로 바꾸는 것입니다.

그런데 파일에는 그 기준 문장이 없었습니다. 명령은 오류 없이 끝났고 화면에는 파일 길이 숫자만 찍혔습니다. 작업 기록에 따르면 파일에는 시작할 때부터 이미 11월 12일 블록이 들어 있었습니다. 바꿀 것이 없던 경우라 피해는 적혀 있지 않습니다. 다만 출력만 놓고는 바뀌었는지, 바뀔 것이 없었는지 가릴 수 없었습니다.

문자열 바꾸기는 기준 문장을 찾지 못해도 오류를 내지 않고 원래 문자열을 그대로 돌려줍니다. 이 글을 쓰면서 임시 파일로 같은 상황을 만들어 보았습니다. 27자짜리 파일에서 없는 기준 문장을 바꾸게 하자 명령은 조용히 끝났습니다. 길이는 27자 그대로였고 새 블록 제목은 파일에 없었습니다. 길이 숫자만 보면 바뀌지 않은 파일도 정상으로 보입니다.

## 아무 출력도 없는 도구는 성공한 것입니까?

아닙니다. 빈 출력은 성공이 아니라 확인되지 않았다는 뜻으로 읽는 편이 안전합니다.

11월 11일 새벽 Threads와 X 글 회차에서, 브라우저를 조작하는 짧은 도구 파일(cdp.mjs)을 `node cdp.mjs x paste`처럼 불렀더니 아무것도 출력되지 않았고 붙여넣기도 일어나지 않았습니다. 이 도구는 첫 번째 인자를 명령으로 읽는데, 앞에 `x`를 끼워 넣는 바람에 `x`가 명령이 된 것입니다. 작업 기록은 이 일로 호출 몇 번을 헛되이 썼다고 적었습니다.

11월 12일에 같은 이름의 파일(11월 8일자 복사본)을 읽어 보았습니다. 첫 인자가 paste, upload, eval 가운데 하나가 아니면 어떤 분기도 실행되지 않고, 연결을 닫은 뒤 정상 종료 코드로 끝납니다. 반대로 대상 탭이 없으면 NO_TAB, 20초를 넘기면 TIMEOUT을 출력합니다. 다른 실패는 말을 하는데 모르는 명령만 조용히 지나가는 구조입니다.

올바르게 부르면 paste는 `pasted`, upload는 `inputs 1` 같은 줄을 찍습니다. 그래서 작업 기록은 빈 출력을 잘못된 명령의 신호로 정리했습니다. 이 도구 파일은 이번에 고치지 않았습니다.

쓰는 쪽에서 막는 방법도 있습니다. 모르는 명령이 들어오면 그 사실을 한 줄 출력하고 비정상 종료 코드로 끝내도록 마지막 분기를 하나 두면, 인자 순서가 틀린 호출은 호출한 자리에서 바로 드러납니다. 이것은 제안일 뿐 이 도구에 적용한 변경이 아닙니다. 적용하기 전까지는 호출하는 쪽이 성공할 때 나오는 말을 기억하고, 그 말이 없으면 성공으로 세지 않는 수밖에 없습니다.

## 실패처럼 보일 때 바로 다시 실행해도 됩니까?

그렇지 않습니다. 다시 실행하기 전에 바깥의 상태를 먼저 읽어야 합니다. 같은 이틀의 기록에서 응답과 결과가 어긋난 나머지 다섯 건은 방향이 서로 달랐습니다.

| 상황 | 응답이 보여 준 것 | 실제 결과 | 다시 하기 전에 읽은 곳 |
|---|---|---|---|
| 유튜브 라이브 채팅 입력(11일) | 오류 없음, 채팅 목록 그대로 | 첫 입력은 올라가지 않았고, 새 스냅샷의 입력칸 참조로 다시 넣자 한 건만 올라감 | 채팅 목록 |
| X 연결 글 여덟 번째 답글(11일) | 작성 화면에 갔다가 원래 글로 돌아옴, 오류 없음 | 두 번 모두 새 답글이 없었고, 같은 순서를 손으로 밟자 올라가 링크 카드도 생김 | 원래 글 화면에서 답글이 없는지 확인 |
| 크롬 화면 캡처(12일) | 시간 초과 응답 | 나중에 지정 경로에 117,545바이트 JPEG 파일이 생김 | 파일 존재와 크기, 열어 본 실제 화면 |
| 네이버 발행 버튼 두 번(11일) | 발행 패널이 아직 열리는 중 | 두 번째 누름이 기본 카테고리로 바로 발행함 | 같은 글을 열어 카테고리와 태그 수정 |
| 장부 메모 옮겨 적기(12일) | 합계 599는 맞음 | 세부 두 항목이 실제 표(10과 589)와 달랐음 | 원본 표의 행 |

앞의 두 건은 조용히 실패했고, 셋째 건은 실패했다는 응답 뒤에 결과가 생겼습니다. 넷째 건은 기다리지 않고 한 번 더 눌러서 의도하지 않은 곳에 결과가 생겼고, 다섯째 건은 합계가 맞아서 세부 값이 틀린 것을 가렸습니다. 응답이 어느 쪽으로 틀리는지는 일정하지 않으므로 응답의 방향으로 짐작하지 않는 편이 낫습니다.

두 번째 사례에서 작업 기록은 중간에 페이지의 알림이 자동으로 수락됐다고 적었고, 페이지를 떠날지 묻는 확인창일 수 있다고 추정했습니다. 확인된 원인은 아니라서 이 글에서도 추정으로만 둡니다. 확인된 것은 재시도 전에 원래 글의 화면을 열어 답글이 없음을 본 뒤 다시 시도했기 때문에 중복 답글이 생기지 않았다는 점입니다.

세 번째 사례의 기록은 파일이 있다는 것만으로 정상 화면이라고 인정하지 않는다는 점도 적었습니다. 이 회차에서는 파일을 열어 실제 화면을 확인했습니다.

네이버 발행 사례에서는 잘못 발행된 글을 지우고 새로 올리지 않았습니다. 기록은 같은 글을 열어 카테고리를 여행정보와 세계여행으로 고치고 태그 20개를 넣었다고 적었고, 발행 패널에서 카테고리를 먼저 고른 뒤 발행 버튼을 정확히 한 번만 누르는 것으로 규칙을 정리했습니다. 장부 메모 사례의 정리는 화면에서 읽은 행의 값을 그대로 옮기고 다른 날짜의 값을 섞지 않는다는 것이었습니다. 합계가 맞는지는 세부 값이 맞는지를 보증하지 못합니다.

## 무엇을 다시 읽으면 됩니까?

다시 읽을 곳은 도구의 응답이 아니라 일이 일어났어야 하는 자리입니다. 위 기록에서 정리한 기준은 아래와 같습니다.

| 작업 | 응답만으로 아는 것 | 다시 읽을 곳 |
|---|---|---|
| 파일의 한 구간 바꾸기 | 명령이 끝났다 | 새로 넣은 표지 문장이 파일에 있는지, 기준 문장이 사라졌는지 |
| 밖에 글이나 답글 올리기 | 버튼이 눌렸다 | 공개 화면의 목록에 내 글이 정확히 한 건 있는지 |
| 사진이나 파일 만들기 | 시간 초과가 났다 | 지정 경로의 파일 존재와 크기, 열어 본 실제 모습 |
| 값을 옮겨 적기 | 합계가 맞다 | 원본 표의 행과 항목별 값 |
| 스크립트 실행하기 | 출력이 비어 있다 | 성공할 때 찍히는 말이 실제로 나왔는지 |

다시 읽는 데에는 호출이 한 번 더 듭니다. 모든 단계에 넣으면 자동화가 그만큼 느려지고 읽을 것도 많아지므로, 바깥에 흔적이 남는 일부터 고르는 편이 현실적입니다. 글을 올리는 일, 파일을 고치는 일, 장부에 숫자를 옮기는 일이 그런 예입니다. 반대로 같은 일을 몇 번 해도 같은 결과가 나오는 읽기 작업은 다시 읽지 않아도 손해가 작습니다. 이 구분도 이번 기록에서 나온 판단이며 다른 업무에서 맞는지는 업무마다 따져 보아야 합니다.

내 업무에 옮기려면 아래 순서가 출발점이 됩니다. 이번 기록에서 정리한 제안이며 고객 프로젝트에서 검증한 절차는 아닙니다.

1. 성공했을 때 도구가 찍어야 할 말과, 바뀌어야 할 값을 먼저 적어 둡니다.
2. 아무 출력이 없으면 성공이 아니라 확인 전으로 기록합니다.
3. 파일 교체는 기준 문장을 못 찾으면 멈추게 합니다. 아래처럼 바꾸기 전후가 같은지만 비교해도 이번 사례는 걸러집니다.
4. 다시 실행하기 전에 바깥 상태를 한 번 읽습니다. 이미 생겼다면 다시 하지 않고, 없다면 그때 다시 합니다.
5. 같은 버튼은 한 번만 누르고, 반응이 느려 보여도 화면을 읽으며 기다립니다.

```powershell
$new = $old.Replace($anchor, $block)
if ($new -eq $old) { throw "기준 문장을 찾지 못해 바뀐 것이 없습니다" }
```

이 두 줄은 임시 파일 상황에서 시험했습니다. 기준 문장이 없으면 멈추고, 있으면 통과합니다. 운영 중인 기억 파일의 실제 작업에 넣었다는 뜻은 아닙니다.

재시작할 때의 확인 순서는 [AI 자동화 재시작 기준](/works/ai-automation-safe-retry)에서, 자동화가 한 일을 도구 바깥의 표에 남기는 방법은 [자동화가 한 일, 한 줄로 남기기](/works/automation-run-record)에서 다뤘습니다. 이 글은 그 사이에서 응답과 결과를 따로 읽는 한 단계를 보탠 것입니다.

## 이 기록이 말하지 못하는 것은 무엇입니까?

일곱 건은 이틀 분량의 기록에서 고른 것이어서 전체 빈도를 말해 주지 않습니다. 이 확인을 넣은 뒤 사고가 줄었는지는 측정하지 않았습니다. 라이브 채팅 사례에서 첫 입력이 왜 올라가지 않았는지, X 답글이 왜 두 번 돌아왔는지는 원인을 확정하지 못했습니다. 기록이 적은 방법으로 해결됐다는 사실만 확인되어 있습니다.

사례에 나온 도구와 화면의 동작은 2026년 11월 11일과 12일 시점의 것입니다. 사이트나 도구가 바뀌면 같은 일이 같은 방식으로 일어나지 않을 수 있습니다.
