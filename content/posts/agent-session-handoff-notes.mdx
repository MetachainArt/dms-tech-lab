며칠에 걸친 일을 에이전트에게 맡기면, 새 세션의 에이전트는 앞 세션에서 무슨 일이 있었는지 모른 채 시작합니다. 그래서 Anthropic이 공개한 장시간 작업 사례는 일의 상태를 대화 바깥의 파일에 남기게 했습니다. 진행 기록, 끝난 일과 남은 일의 목록, 변경 이력이 그 파일입니다. 이 글은 그 근거를 읽고, 맡길 일마다 다섯 칸을 채우는 인수인계 카드를 DMS.Labs의 제안으로 붙였습니다. 카드는 직접 시험한 것이 아니며, 읽은 사례도 소프트웨어 개발에서 나왔습니다.

2026년 11월 25일 확인한 공개 자료 기준입니다. 읽은 자료는 Anthropic 엔지니어링 글 두 편(2025년 11월 26일, 2025년 9월 29일)과 검색 기술 회사 Chroma의 기술 보고서 「Context Rot」(2025년 7월)입니다. 뒤에 나오는 카드와 가상의 장면은 이 자료를 읽고 만든 DMS.Labs의 제안이며, 어느 자료가 요구하는 규격이 아닙니다.

![창가 나무 책상 위에 펼친 공책과 연필, 놋쇠 열쇠 하나가 놓여 있고 뒤에 도자기 화병과 초록색 작은 통이 보이는 장면](/images/posts/agent-session-handoff-notes/handoff-notebook-on-desk.webp)

## 새 세션의 에이전트는 앞 세션에서 한 일을 어떻게 압니까?

스스로는 알 수 없고, 대화 바깥에 남은 자료를 읽는 수밖에 없습니다. Anthropic은 장시간 일하는 에이전트의 어려움을 이렇게 설명합니다. 에이전트는 세션 단위로 일하고, 새 세션은 앞의 일을 기억하지 못한 채 시작합니다. 글은 교대로 일하는 엔지니어들을 떠올리게 합니다. 새로 온 사람이 앞 교대에 일어난 일을 전혀 모르는 프로젝트입니다. 컨텍스트 창(모델이 한 번에 볼 수 있는 글의 범위)에는 한도가 있고 복잡한 프로젝트는 한 창 안에서 끝나지 않으니, 세션 사이를 잇는 방법이 필요하다고 적습니다.

단서가 하나 있습니다. 이 설명은 Claude Agent SDK로 만든 환경을 두고 한 것입니다. 쓰는 제품에 따라 지침 파일을 시작할 때 불러오는 기능이나 기억 기능이 있을 수 있어서, 모든 에이전트가 똑같이 앞일을 잊는다고 일반화하지는 않겠습니다. 그런 기능이 있어도 불러올 내용은 누군가 미리 써 두어야 합니다.

## 앞 대화를 요약해서 이어 가면 되지 않습니까?

요약만으로는 부족했다는 것이 Anthropic의 경험입니다. 대화를 요약해 새 창에서 이어 가는 방식(압축)은 이론상 에이전트가 아주 오래 일하게 해 줄 것처럼 보입니다. 그러나 글은 Opus 4.5 모델을 Claude Agent SDK에 넣고 여러 컨텍스트 창에 걸쳐 반복 실행해도, claude.ai를 복제하라는 식의 큰 지시 하나만 주면 제품 수준의 웹앱에 못 미쳤다고 씁니다. 압축이 다음 에이전트에게 늘 분명한 지시를 넘기지는 않는다는 설명도 붙습니다.

다른 글은 압축의 어려움을 이렇게 짚습니다. 무엇을 남기고 무엇을 버릴지가 기술이며, 지나치게 줄이면 나중에야 중요해지는 사소한 맥락을 잃을 수 있습니다. Claude Code는 설계 결정, 풀리지 않은 버그, 구현 세부를 남기고 반복된 도구 출력은 버리며, 최근에 연 파일 다섯 개를 함께 넘긴다고 합니다.

길어진 문맥에는 또 다른 문제가 있습니다. Chroma 보고서는 18개 모델을 시험하면서 과제의 난이도는 고정하고 입력 길이만 바꿨습니다. 모든 실험에서 입력이 길어질수록 성능이 떨어졌고, 떨어지는 모양은 고르지 않았다고 정리합니다. 저자들은 원인을 설명하지 못한다고 밝히고, 실제 업무는 더 복잡하므로 하락이 더 클 것으로 예상합니다. 이 예상은 저자의 것이며 이 보고서가 시험한 결과가 아닙니다. 학술지 논문이 아니라 회사가 낸 기술 보고서라는 점도 감안해야 합니다. Anthropic의 글도 같은 현상을 컨텍스트 부패(context rot)라 부르며, 모델마다 정도는 다르지만 모든 모델에서 나타난다고 봅니다.

그래서 저는 이 자료들이 중요한 상태를 대화 안에 두지 말고 따로 적어 두라는 쪽을 가리킨다고 읽었습니다. 에이전트가 기억을 어떻게 불러오는지에 대한 설계는 [기억은 저장보다 회수가 어렵다](/blog/agentic-era-memory-retrieval-architecture)에서 다뤘고, 이 글은 세션이 바뀌는 순간에 무엇을 남기느냐에 집중합니다.

## 긴 일을 맡기면 어디서 어긋납니까?

Anthropic이 관찰한 실패는 세 가지입니다. 첫째는 한 번에 너무 많이 하려는 경향입니다. 앱 전체를 단번에 만들려다 구현 도중 컨텍스트가 바닥나면, 다음 세션은 반쯤 만들어졌고 기록도 없는 상태에서 시작합니다. 다음 에이전트는 무슨 일이 있었는지 짐작해야 했고, 기본 기능을 다시 돌려 놓는 데 시간을 썼다고 합니다.

둘째는 프로젝트 후반에 나타났습니다. 이미 일부가 만들어진 뒤, 나중에 온 에이전트가 주변을 둘러보고 진전이 있다는 이유로 일이 끝났다고 선언했습니다.

셋째는 제대로 시험하지 않고 완료 표시를 하는 것입니다. 단위 시험이나 curl 요청으로 확인하고도, 처음부터 끝까지 이어서 쓰면 동작하지 않는다는 사실은 알아채지 못했습니다. 브라우저 자동화 도구로 사람이 쓰듯 시험하라고 시키자 나아졌습니다. 다만 이 도구로는 브라우저 자체의 경고창을 볼 수 없었고, 그 경고창에 기대는 기능은 오류가 더 많았다고 글은 한계도 적습니다.

업무로 옮기면 비슷한 모양이 됩니다. 정리하던 서류를 절반만 고친 채 끊깁니다. 폴더에 결과 파일이 몇 개 보인다는 이유로 다 했다고 보고합니다. 열어 보지 않고 완료로 표시합니다. 이것은 제가 위 사례를 업무 말로 바꿔 본 것입니다. 같은 일이 업무 자동화에서 얼마나 자주 생기는지는 읽은 자료에 없습니다.

## Anthropic은 세션 사이에 무엇을 남기게 했습니까?

![초록빛 벽의 나무 걸이에 놋쇠 열쇠 두 개가 걸려 있고 한 자리는 비어 있으며, 아래 선반에 접힌 종이와 작은 그릇이 놓인 장면](/images/posts/agent-session-handoff-notes/key-hooks-by-door.webp)

진행 기록 파일, 기능 목록 파일, 변경 이력을 남기게 했습니다. 첫 세션은 초기 환경을 만드는 전용 에이전트가 맡습니다. 개발 서버를 켜는 스크립트(init.sh), 앞서 한 일을 적는 claude-progress.txt, 처음 추가한 파일을 보여 주는 첫 git 커밋을 만듭니다. 이후 세션은 한 번에 기능 하나만 진행하고, 끝날 때 병합해도 될 만큼 정돈된 상태를 남기며, 설명을 붙인 커밋과 진행 요약을 씁니다. 이렇게 하면 잘못된 변경을 git으로 되돌릴 수 있었다고 합니다.

기능 목록은 사용자의 첫 지시를 요구 사항으로 펼친 파일입니다. claude.ai를 복제하는 예에서는 항목이 200개가 넘었고, 항목마다 확인 절차를 적고 처음에는 모두 통과하지 않음(passes: false)으로 두었습니다. 이후 에이전트에게는 passes 값만 바꾸고 항목을 지우거나 고치지 말라고 강한 어조로 지시했습니다. 형식은 JSON으로 정했는데, 모델이 JSON 파일은 마크다운 파일보다 덜 부적절하게 바꾸거나 덮어쓰는 경향이 있었기 때문이라고 합니다. 글에는 이 방식이 얼마나 낫다는 수치가 없고, 내부 실험에서 얻은 접근이라는 설명이 전부입니다.

다른 글은 같은 생각을 구조화된 메모(structured note-taking)라고 부릅니다. 에이전트가 컨텍스트 창 바깥에 메모를 정기적으로 쓰고 필요할 때 다시 읽어 오는 방법입니다. 할 일 목록이나 NOTES.md 파일이 그 예입니다. 글은 Claude가 포켓몬 게임을 하는 사례를 들어, 컨텍스트가 초기화된 뒤에도 에이전트가 자기 메모를 읽고 몇 시간짜리 훈련이나 탐험을 이어 간다고 소개합니다. 어떤 방법을 고를지도 적혀 있습니다. 오가는 대화가 많은 일에는 압축, 이정표가 분명한 반복 개발에는 메모, 병렬로 탐색하면 이득이 큰 복잡한 조사와 분석에는 여러 에이전트가 맞는다고 합니다. 여러 에이전트 방식에서는 하위 에이전트가 오래 탐색한 뒤 대개 1,000에서 2,000토큰 안팎의 요약만 돌려줍니다.

## 새 세션은 시작할 때 무엇을 합니까?

읽고, 확인하고, 하나만 고릅니다. 글이 보인 시작 순서는 이렇습니다. 일하는 폴더를 확인합니다. git 기록과 진행 파일을 읽어 최근 일을 파악합니다. 기능 목록을 읽고 아직 안 된 것 가운데 우선순위가 가장 높은 하나를 고릅니다. 그다음 개발 서버를 켜서 기본 동작을 처음부터 끝까지 한 번 시험한 뒤에야 새 일을 시작합니다. 앞 세션이 망가진 상태로 일을 남겼는지 먼저 알아야 하기 때문입니다. 그 위에 새 기능을 얹으면 문제가 더 커진다고 글은 설명합니다.

Anthropic은 어긋남마다 처방을 표로 요약합니다. 아래는 그 표를 한국어로 옮긴 것입니다.

| 어긋남 | 처음 세션에서 남기는 것 | 이후 세션이 하는 일 |
| --- | --- | --- |
| 일 전체가 끝났다고 너무 일찍 선언합니다 | 기능 목록 파일 | 세션을 시작할 때 목록을 읽고 기능 하나만 고릅니다 |
| 오류가 있거나 기록 없는 진행을 남깁니다 | git 저장소와 진행 기록 파일 | 시작할 때 진행 기록과 커밋 기록을 읽고 기본 시험을 돌립니다. 끝날 때 커밋과 진행 갱신을 남깁니다 |
| 기능을 서둘러 완료로 표시합니다 | 기능 목록 파일 | 모든 기능을 스스로 확인하고, 꼼꼼히 시험한 뒤에만 통과로 바꿉니다 |
| 앱을 실행하는 방법을 매번 알아내느라 시간을 씁니다 | init.sh 스크립트 | 시작할 때 init.sh를 읽습니다 |

## 내 업무 자동화에는 어떻게 옮깁니까?

맡길 일 하나마다 아래 다섯 칸을 적은 카드를 만들어, 세션이 바뀔 때마다 갱신하는 방식을 제안합니다. 이 카드는 위 자료를 읽고 DMS.Labs가 만든 것이며, 어느 자료가 시험한 문서가 아닙니다.

| 칸 | 적을 것 | 이 칸을 둔 이유 |
| --- | --- | --- |
| 1. 끝 조건 | 이 일이 끝났다고 말할 수 있는 항목을 하나씩 나열합니다. 처음에는 모두 '아직'으로 둡니다 | 일부만 하고 끝났다고 말하는 일을 줄입니다. Anthropic의 기능 목록에서 가져왔습니다 |
| 2. 끝낸 일 | 항목마다 무엇을 열어 보고 확인했는지 함께 적습니다. 확인한 방법이 없으면 '끝'으로 바꾸지 않습니다 | 시험 없이 완료로 표시하는 문제를 겨냥합니다 |
| 3. 하다 만 일 | 어디까지 했고 무엇을 건드렸는지(파일, 시트, 항목 번호)를 적습니다 | 반쯤 한 일이 기록 없이 남는 문제를 겨냥합니다 |
| 4. 되돌리는 길 | 바꾸기 전 원본이나 사본이 있는 곳을 적습니다 | git으로 잘못된 변경을 되돌린 사례에서 가져왔습니다 |
| 5. 다음 첫 행동 | 새 세션이 가장 먼저 열 파일 하나, 먼저 다시 확인할 항목 하나를 적습니다 | 시작 순서(읽고, 확인하고, 하나만 고른다)에서 가져왔습니다 |

세션을 시작하는 지시문에는 순서를 이렇게 넣습니다. 카드를 읽고, 가장 최근에 '끝'으로 바꾼 항목 하나를 다시 확인하고, 아직 안 끝난 항목 하나만 진행하고, 끝낼 때 카드를 갱신합니다. 1번과 2번 칸은 줄글보다 항목과 상태가 분명한 표나 JSON 같은 형식이 낫다고 생각합니다. 다만 이 근거는 JSON을 덜 덮어썼다는 Anthropic의 경험 하나뿐이고, 다른 형식과 견준 시험은 읽지 못했습니다.

가상의 장면으로 써 보겠습니다. 직원 네 명의 인테리어 업체가 월말 거래처 정산 서류 60건을 에이전트에게 사흘에 걸쳐 정리하게 한다고 가정합니다. 실제 사례가 아니라 설명을 위해 만든 장면입니다. 첫날 17건을 정리하고, 열여덟 번째 서류를 고치던 중에 세션이 끊겼습니다. 카드가 없다면 다음 세션은 폴더에 정리된 파일이 몇 개 있는지만 보고 진행 상황을 짐작합니다. 열여덟 번째 서류를 절반만 고친 줄 모르고 열아홉 번째로 넘어갈 수도 있습니다.

카드가 있다면 칸이 이렇게 채워져 있습니다. 끝낸 일에는 1번부터 17번이 적혀 있고, 항목마다 정리본 합계를 원본 합계와 맞춰 보았다고 쓰여 있습니다. 하다 만 일에는 18번 서류에서 금액 열만 고쳤고 날짜 열은 손대지 않았다고 적혀 있습니다. 되돌리는 길에는 원본 폴더 사본의 위치가 있습니다. 다음 첫 행동은 17번 합계를 다시 맞춰 본 뒤 18번의 날짜 열부터 이어 가는 것입니다. 이어받는 쪽이 짐작할 부분을 줄이는 것이 이 카드가 노리는 효과입니다. 이 카드가 실제 업무에서 어긋남을 얼마나 줄이는지는 직접 시험하지 않았습니다.

## 이 방식이 해결하지 못하는 것은 무엇입니까?

첫째는 카드가 틀릴 수 있다는 점입니다. 앞 세션이 쓴 '끝' 표시를 새 세션이 그대로 믿으면 오류가 다음 세션으로 넘어갑니다. Anthropic이 시작할 때 기본 시험을 먼저 돌리게 한 것도 같은 이유로 읽힙니다. 카드의 2번 칸에 확인 방법을 적게 한 것도 그래서입니다. 확인이 맞았는지는 따로 봐야 하며, 누가 어떻게 볼지는 [AI 결과 검수자 정하기](/works/ai-output-reviewer-card)에, 성공 표시 뒤에 결과를 다시 읽어 보는 방법은 [성공 출력 뒤에 다시 읽기](/works/read-back-after-success)에 정리했습니다.

둘째는 확인할 수 없는 화면입니다. Anthropic이 인정한 브라우저 경고창 같은 틈은 카드를 써도 남습니다. 자동화가 실제로 무엇을 했는지 남기는 일은 [자동화가 한 일, 한 줄로 남기기](/works/automation-run-record)와 함께 쓰면 보완이 됩니다.

셋째는 비용입니다. 카드를 쓰고 읽는 데 드는 시간과 토큰이 얼마인지는 읽은 자료에 없습니다. 하루 안에 끝나는 일에는 카드가 과할 수 있습니다. 며칠에 걸치거나 세션이 여러 번 바뀌는 일에만 쓰는 것이 맞다고 생각합니다.

넷째는 적용 범위입니다. 읽은 사례는 웹 앱 개발입니다. Anthropic은 과학 연구나 금융 모델링 같은 일에도 이 교훈이 적용될 가능성이 있다고 쓰지만, 이는 전망이며 제가 읽은 범위에서는 그 시험을 확인하지 못했습니다. 모든 일을 에이전트 하나가 맡는 편이 나은지, 역할을 나눈 여러 에이전트가 나은지도 글이 열린 질문으로 남겼습니다. 에이전트가 막혔을 때 사람에게 넘기는 방법은 [CH7 인간 핸드오프와 에스컬레이션 설계](/blog/agentic-era-ch7-human-handoff-and-escalation-design)를 보시기 바랍니다.

## 이번 주에 무엇을 해 볼 수 있습니까?

하루 이상 걸리거나 세션이 여러 번 바뀔 일 하나를 골라 다섯 칸 카드를 만듭니다. 1번 칸은 끝 조건을 항목으로 나누는 데서 시작하는 것이 가장 쉽습니다. 다음 세션 시작 지시문에는 카드를 읽고, 최근에 끝난 항목 하나를 다시 확인한 뒤, 남은 항목 하나만 진행하라고 적습니다.

이 글이 확인하지 못한 것을 정리하면 이렇습니다. 카드를 실제 업무에 적용해 시험하지 않았습니다. 읽은 자료는 모두 2025년에 나왔고(한 편은 2026년 10월 수정 표시), 이후 모델과 도구가 달라졌을 수 있습니다. Anthropic 글의 성과는 수치 없이 서술된 것입니다. Chroma 보고서는 짧은 과제를 길게 늘려 본 시험이라 실제 업무와 같다고 할 수 없습니다. 인테리어 업체 장면과 표는 DMS.Labs의 제안과 가정이며 고객 사례나 현장 측정이 아닙니다.
